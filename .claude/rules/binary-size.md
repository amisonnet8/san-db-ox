# 実行ファイルサイズ

SanDBoxは「単一バイナリ完結・軽量」がコアコンセプト（仕様書§1）。バイナリ
サイズの最小化を積極的に追求する必要はないが、**むやみに肥大化する実装は
避ける**こと。

## 判断の目安

- 新しい依存ライブラリを追加する前に、標準ライブラリだけで実現できないか
  を一度検討すること。
- 依存を追加する場合、そのライブラリ自体のサイズや、さらにその先の推移的
  依存（transitive dependencies）がどれだけ増えるかも考慮すること。
- 色付け・罫線・TUI等の装飾ライブラリは導入しない（詳細は `cli-output.md`
  参照）。これは典型的な「むやみな肥大化」の例。
- 「配布方法」（`distribution.md`）で各OS/アーキテクチャ向けバイナリを
  複数ビルド・配布する設計上、バイナリサイズの増加は配布コストにも直結する。
- **JSONの読み書きは標準ライブラリ（`encoding/json`）で完結させる。**
  stdioプロトコル（仕様書§7）が扱うJSONは、行区切りの単純な構造しか
  持たない。高速化目的のサードパーティJSONライブラリは導入しない。

## サイズが増える主因はSQLiteドライバである

`modernc.org/sqlite`（Pure-Go SQLite）を含むバイナリは10〜15MB級になる。
これは仕様書§11で「CGO不要でクロスコンパイルが容易」という利点と引き換えに
受け入れた前提であり、この選択自体を覆さない限りサイズは下がらない。
したがって、**それ以外の依存を足すときの心理的ハードルを下げないこと**——
「どうせ既に十数MBあるのだから」という理由で装飾ライブラリ等を追加しない。

## 優先度

サイズ最適化そのものを目的化しない。まず正しく動くこと、仕様
（`san-db-ox_spec_ja.md`）に忠実であることを優先し、その上で「同じ機能を実現
するのに不必要に重い依存を選んでいないか」を都度意識する、という程度の
バランスでよい。
