# ディレクトリ構成

SanDBoxは「`engine`ライブラリが核、スタンドアロン実行ファイル（REPL＋バッチ
実行＋stdioプロトコル）はそのライブラリを使った1つのアプリケーション」という
構造を取る（仕様書§10参照）。新しいファイルを追加する際は、必ずこの構造の
どちらに属するかを意識すること。

```
san-db-ox/
├── CLAUDE.md               ← プロジェクトルール（参照先の案内）
├── PLAN.md                 ← 実装計画・進捗管理（開発フェーズ、現在地、保留事項）
├── Makefile
├── LICENSE                 （MIT）
├── go.mod
├── go.sum
├── .gitignore
├── .gitattributes          （`* text=auto eol=lf`。理由は `testing.md` 参照）
├── README.md               ← クイックスタート（英語）
├── README_ja.md            ← クイックスタート（日本語）
├── docs/                     ← 利用者向けドキュメント
│   ├── spec/                   ← san-db-ox_spec_ja.md（開発者・高度な利用者向けの設計・仕様書）
│   ├── usage/                   ← CLIコマンド・オプションのリファレンス
│   ├── examples/                 ← 実例集（実装完了後に作成）
│   └── tour/                     ← 入門ガイド（体験型、実装完了後に作成）
├── .devcontainer/
│   └── devcontainer.json
├── .vscode/
│   └── settings.json
├── .claude/
│   ├── settings.json
│   └── rules/
├── engine/                 ← 【ライブラリ本体】インメモリSQLエンジン
├── cmd/san-db-ox/          ← 【アプリ】engineを利用した単一バイナリRDBMSの実装
├── tests/                    ← `make test` が実行するE2E/結合テスト一式
└── .github/workflows/       ← CI定義（test.yml, release.yml 等）
```

`engine/`・`cmd/san-db-ox/` 配下の具体的なファイル構成は、実装を進めながら
決めてよい。ここでは「どちらのディレクトリに属するか」という配置の判断基準
のみを定める。

## 配置の判断基準

- **ネットワークI/Fに一切触れないコード** → `engine/`
- **REPL・バッチ実行・stdioプロトコル・CLIオプションなど、`engine`を使う側の
  ロジック** → `cmd/san-db-ox/`
- **`engine`パッケージから `net`/`net/http` 等への依存を追加しないこと**
  （仕様書§10の「ネットワークI/Fを持たないことによる安全性」という設計原則を
  壊すため）。
- **`cmd/san-db-ox` も同様に `net` を直接importしない。** SanDBoxは製品全体と
  してネットワーク待受を持たない。外部公開はsocat等でトランスポートを外付け
  する運用に委ねる（仕様書§8）。**CIで「`net/http`が推移的にも現れないこと」
  「`net`を直接importしていないこと」を検証する**（`testing.md`参照）。
  - 例外として、推移的依存には`net`パッケージが含まれる（`modernc.org/sqlite`
    が使う`modernc.org/libc`経由）。これはSQLiteドライバ実装自体の都合であり、
    ネットワークI/Oを行うコードを持つことを意味しない。検証はこの経路を
    許容する形で書くこと。

## 3つの実行モードは同じドットコマンド実装を共有する

REPL・バッチ実行・stdioプロトコルは入出力の形が違うだけで、実行できる操作は
同じである（仕様書§2、§3）。**ドットコマンドの実装をモードごとに重複させない
こと。** モード固有なのは「入力をどう読むか」「結果をどう書くか」だけで、
その間の処理は共通化する。

## 各ファイル・ディレクトリの補足

- **go.sum**: リポジトリにコミットする。依存パッケージのハッシュ値による
  改ざん検知・再現可能なビルドを担保するファイルであり、`go.mod` とセットで
  コミットするのがGoの標準的な慣習。除外しない。
- **.gitattributes**: `* text=auto eol=lf` を置く。Windowsランナーでの
  チェックアウト時にCRLFへ変換されると`gofmt -l`が全ファイルを未整形と
  誤検知するため（詳細は `testing.md`）。**最初のpush前に置くこと。**
- **README.md / README_ja.md**: 英語版・日本語版を両方用意する。仕様の詳細
  ではなく、インストール・最初の一歩に絞ったクイックスタートに徹し、
  詳細は`docs/`配下の各ドキュメントへリンクする。
- **.devcontainer/**: 開発コンテナ定義（Go環境のみ。単一の`devcontainer.json`）。
- **.vscode/**: エディタ設定（推奨拡張機能等、チームで共有したい設定のみ）。
- **docs/**: 利用者向けドキュメント一式。4つのディレクトリに分かれ、対象読者・
  目的が異なる。
  - **docs/spec/**: `san-db-ox_spec_ja.md`（開発者・高度な利用者向けの設計・
    仕様書）。**実装しながら育てるドキュメント**であり、設計判断を変えたら
    まずここを更新してから着手する。`.claude/rules/`側からは
    `san-db-ox_spec_ja.md§N`という節番号で引用する。
  - **docs/usage/**: CLI起動オプション・REPLドットコマンド・stdioプロトコルの
    opのリファレンス。仕様書（`docs/spec/`）が設計判断の理由まで説明する散文
    なのに対し、こちらは「今すぐ使うための」テーブル中心の索引的なドキュメント。
  - **docs/examples/**: 実例集（CI/CDでのInstant Test DB、`.snapshot`による
    バグ再現共有、stdio経由での他プログラム結合、SQL学習サンドボックス等。
    仕様書§9の各ユースケースを、実際に打つコマンド付きで肉付けしたもの）。
    **実装完了後に作成する。**
  - **docs/tour/**: 入門ガイド（体験型、順を追って学ぶ形式）。`README.md`
    （索引）＋番号付きの章立てで、1つ前の章を前提に次の章へ進む構成——
    `docs/usage/`（索引的なリファレンス）・`docs/examples/`（1本ずつ自己完結
    したユースケース）とは読む順序が意味を持つ点が異なる。**実装完了後に
    作成する。** 各章のコマンド・出力例は、他の`docs/`配下の文書と同様、
    実際にビルドしたバイナリへ流し込んで実測検証したものをそのまま載せる。
- **tests/**: `make test` が実行するE2E/結合テスト一式。**`docs/examples/`とは
  役割が異なる**——`tests/`はCIが自動実行する検証専用、`docs/examples/`は人間が
  読んで手元で試すための実例集。
- **配布物（各OS向けビルド済みバイナリ）**: リポジトリに直接コミットしない
  （詳細は `distribution.md` 参照）。

## 別プロジェクトとの関係

各言語向けのクライアントドライバは、本リポジトリには含めず
`san-db-ox-clients`（別リポジトリ）で提供する。本リポジトリには**プロトコル
仕様（`docs/spec/`）のみ**を置く。

「SanDBoxリポジトリ自体はGoツールチェーンだけで完結する」という単純さを保つ
のが狙い——複数言語ぶんのランタイム導入は本体のビルド・テストには一切不要
であるため。本体側に残す接続テストはGoで書いたstdioクライアントのみとする
（`testing.md`参照）。`san-db-ox-clients`は独立したリポジトリとして扱い、
本リポジトリ配下にcloneして併用する運用は行わない。
