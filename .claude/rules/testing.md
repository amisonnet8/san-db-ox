# テスト方針

## 開発環境の前提

開発者の手元環境は**Linuxのみ**。Windows/macOSでの実際の動作確認は、手元では
行わず GitHub Actions（`windows-latest`/`macos-latest` 等のホステッドランナー）
に委ねる。パブリックリポジトリ（MITライセンス）のため、GitHub Actionsは実質
無制限に利用できる。

| 対象 | 進め方 |
| :--- | :--- |
| コアロジック（`engine`パッケージ、フッター読み書き、`.overwrite`のrename退避方式等） | まずLinux環境・Goのみで開発し、ロジックの正しさを固める。フィードバックループを最速に保つ。 |
| クロスプラットフォーム動作確認（Windows/macOS） | 開発初期からGitHub Actionsで自動テストを組み、都度確認する。特に`.overwrite`はWindows特有のOS制約（`ERROR_SHARING_VIOLATION`等）が設計に直結しているため、後回しにせず早期から継続的に検証する。 |
| stdioプロトコル | Goで書いたクライアントで検証する（`tests/`配下）。他言語ドライバでの検証は別リポジトリ`san-db-ox-clients`が独自に行う（本体CIには含めない）。 |
| 依存ライブラリの脆弱性・ライセンスチェック | GitHub Actions上で `trivy` を実行し、既知の脆弱性（CVE）とライセンス互換性（MIT/BSD/Apache-2.0等は許可、GPL系等は拒否）をチェックする。ソースコード自体のコピペ検出は対象外（人間レビューに委ねる）。 |
| シェルスクリプトの静的解析 | `make shellcheck`（`git ls-files '*.sh'`で追跡中の`*.sh`を自動列挙し`shellcheck`にかける。新規スクリプトを追加してもMakefile側の変更は不要）。`check`には含めず、CIでは`ubuntu-latest`限定の専用ジョブとして独立させる——`windows-latest`に`shellcheck`がプリインストールされている保証が無く、かつスクリプトの中身はOSによって変わらないため、3OSマトリクスで重複実行する意味が無い。devcontainerの`postCreate.sh`でもインストールし、手元で`make shellcheck`が使えるようにしておく。 |

**シェルスクリプト中のコメントを、行頭が小文字の `# shellcheck` で始まる文に
してはいけない。** ShellCheck自身が`# shellcheck disable=...`のような
インラインディレクティブとして解釈しようとし、`key=value`形式でない
（コロン区切りの説明文等の）場合はパースエラー（SC1072/SC1073）で落ちる
——ディレクティブ扱いされたコメント以降の行がパース不能になり、その
スクリプト全体がチェックできなくなる（`.devcontainer/postCreate.sh`で
`shellcheck`パッケージの導入理由を説明するコメントを書いた際に実際に踏んだ）。
「ShellCheck」等、大文字を混ぜて書けばディレクティブとして認識されず
通常のコメントとして扱われる。

## 実装後の動作確認について

実装したら、必ずビルド確認（`make build` 等）に加えて実際の動作確認を行うこと。
ロジック上正しそうに見えても、実際に動かして初めて見つかる不具合は起こりうる。

- ビルド確認（`make build`）は`.claude/settings.json`の`PostToolUse`フックで
  `.go`/`go.mod`/`go.sum`編集時に自動実行されるよう設定する（実装の最初の
  ステップで入れること）。`make test`（e2e、数十秒かかる）はフック化せず、
  手動で判断して実行する。
- `make test`（`tests/` を通した実動作確認）を走らせる粒度は、作業規模に
  応じて判断する。
  - 小規模な修正（数行の変更、1関数内で完結する変更）は、一連の作業が終わった
    最後に1回でよい。
  - 大規模な変更（複数ファイルにまたがる、設計に関わる変更）は、各ステップの
    区切りごとに実行すること。
  - 判断に迷ったら、実行する側に倒すこと。

## SanDBox固有の検証項目

### `net` を持ち込んでいないことの検証

仕様書§10の設計原則「ネットワークI/Fを持たないことによる安全性」は、
**コードレベルで検証可能であることが価値の源泉**である。CIで機械的に確認すること。

- `engine`・`cmd/san-db-ox` のいずれも `net`/`net/http` を直接importしていない
  こと。
- `net/http` が推移的依存にも現れないこと。
- ただし `net` は推移的依存に含まれる（`modernc.org/sqlite` → `modernc.org/libc`
  経由）。この経路は許容する形で検証を書くこと。**「`net`が一切現れない」と
  いう検証は失敗する。**

### `.overwrite` のテストは必ずコピーに対して行う

`.overwrite`は対象ファイルの中身を書き換えるため、ビルド成果物そのものに
対して実行すると、次の`make build`まで壊れた状態が残る。テスト用の一時
ディレクトリへコピーしてから実行すること。

**`go test` から `.overwrite` の実挙動は検証できない。** `go test`は一時的な
テストバイナリを生成して実行するため、`os.Executable()`が指すのはテスト
バイナリ自身である。加えて仕様書§11により、`go run`が生成した一時バイナリに
対する`.overwrite`は明示的に拒否する仕様になっている。**実挙動の検証は、
`make build`した実バイナリをコピーして叩くE2Eテスト（`tests/`）側で行うこと。**
`engine`のユニットテストでは、退避・書き込み・ロールバックの各手順を個別に
検証するに留める。

### 複数プロセスが同一バイナリから同時起動される状況

stdioプロトコルは、socat等でトランスポートを外付けして使われることを想定して
いる（仕様書§8）。socatの`fork`は接続ごとにプロセスを生成するため、**同じ
バイナリから複数のプロセスが同時に起動し、それぞれが独立したインメモリDBを
持つ**状況が日常的に発生する。

- 複数プロセスを同時起動して、それぞれが独立したDBを持つこと（一方の
  INSERTが他方から見えないこと）を確認する。
- 同じバイナリを複数プロセスが同時に読み込む（フッター読み出し）際に競合が
  起きないことを確認する。
- **`.snapshot`を複数プロセスが同時に同じパスへ実行した場合**の挙動を確認する。
  仕様書§11のとおり一時ファイル＋`rename`のアトミック方式を採っていれば、
  壊れたファイルが観測されることはないはず。

### stdioプロトコルの検証

- **フラッシュ漏れによるデッドロックを検出できるテストを書く。** 本体が
  レスポンスを書いた後にフラッシュしていないと、クライアントは応答を
  待ち続ける。テストには必ずタイムアウトを設け、ハングを失敗として
  検出できるようにすること（無限に待つテストはCIを止める）。
- stdoutにプロトコル応答以外が混入していないことを確認する。デバッグ用の
  出力が1行紛れただけでクライアントのパースが壊れる。
- 値のJSON表現（NULL/INTEGER/REAL/TEXT/BLOB）の往復を検証する。特に
  **BLOBの1要素配列表現が`params`でも受け付けられること**（読み出した値を
  そのまま書き戻せること）。
- `close` op・stdinのEOF・`overwrite` op のそれぞれで、プロセスが正しく
  終了することを確認する。
- 不正なJSONを送った場合にエラー応答を返し、**接続を切らずに次のリクエストを
  受け付ける**ことを確認する。

### `--read-only` の検証

書き込みSQL・`.snapshot`・`.overwrite`・`.load`・`.snapshot --sqlite`の
すべてが拒否されることを確認する。**`.snapshot --sqlite`（ファイル書き出し）
が拒否対象に含まれる**のは、DBを変更しないが外部公開時にサーバー側の
ファイルシステムへ書き込む手段になるためである（仕様書§2）。テストから
漏らさないこと。

## `tests/e2e.sh`（`make test`）実装時の落とし穴

> **出所:** 以下は本プロジェクトの前身である **ExecDB** の開発中に実際に踏んだ
> 事象である（SanDBoxで発生したものではない）。いずれもSanDBoxの構成でも
> 同様に起こりうるため、記録として引き継ぐ。シェルスクリプトでE2Eを書く際は
> 事前に目を通すこと。

- **バックグラウンドで起動した子プロセスのPIDを`pid=$(start_child ...)`の
  ようにコマンド置換で受け取った場合、そのPIDは呼び出し元シェルの
  「子プロセス」ではなくなる**（コマンド置換はサブシェルを生成するため）。
  そのPIDに対してbashの`wait`組み込みコマンドを使うと`wait: pid ###: not a
  child of this shell`で失敗する（`2>/dev/null`で隠しても`set -e`下では
  地雷になりうる）。代わりに`kill -0 "$pid"`をポーリングして「プロセスが
  消えるまで待つ」方式を使うこと（`kill -0`は親子関係を問わず任意の可視PIDに
  使える）。
- **`set -e`（errexit）下で、`out="$(コマンド)"`のようなコマンド置換への
  代入は、内部コマンドが非ゼロで終了すると代入文自体が失敗扱いになり
  スクリプトが即終了する。** エラー時の出力を検証したいテスト（バッチ実行が
  終了コード1を返すことの確認など）では、`out="$(cmd ... 2>&1 || true)"`の
  ように内側で明示的に握りつぶす必要がある（`grep -q`とのパイプに
  `pipefail`が絡むケースも同様に要注意）。
- **プロセスを一時ディレクトリで動かす。** `.snapshot`はファイル名を省略すると
  カレントディレクトリに生成する。テストスクリプトの実行時カレント
  ディレクトリのまま起動すると、リポジトリ直下にファイルが生成されてしまう。
  `(cd "$WORK" && exec "$@")`のようにサブシェルで作業ディレクトリを切り替えて
  から`exec`すること（`exec`で置き換えないと`$!`がサブシェルのPIDになり、
  シグナル送信・生存確認の対象がずれる）。
- **`fail()`で`exit 1`する設計だと、それより前で起動済みのバックグラウンド
  プロセスが停止されないまま孤児として残る。** 起動したPIDを配列に記録して
  おき、スクリプト全体の`trap ... EXIT`で無条件にkillする「安全網」を、個別の
  停止呼び出しとは別に必ず用意すること。
- **パイプの各段は別のサブシェルで実行され、`set -e`（errexit）はそのサブシェルにも
  継承される。** `cmd1 | { cmd2; echo $? >file; }`のように、パイプ右側の終了コードを
  ファイル経由で受け取ろうとしても、`cmd2`が「期待どおりの非ゼロ終了」（例:
  意図的にプロセスを異常終了させて確認するテストでの`exit 1`）をした時点で、
  継承された`set -e`がそのサブシェルを`echo $? >file`に到達する前に中断させて
  しまう。エラーメッセージも出ず、外側のスクリプトの`trap ... EXIT`が静かに
  発火して終了するため、原因の見当がつきにくい（REPLのCtrl+C状態機械を
  PTY経由でテストする際に必ず踏む——2回連続のCtrl+Cで`exit 1`する「正しい」
  挙動そのものがテストスクリプトを巻き込んで落とす）。
  **対処: その終了コードを読みたいサブシェルの先頭で`set +e`し、危険な
  コマンドの終了をerrexitの対象から明示的に外してから`$?`を読む**
  （`{ set +e; cmd2; echo $? >file; }`）。なお`"$?"`をパイプライン直後に
  素朴に読む方法・`PIPESTATUS`配列を読む方法は、それぞれ「非ゼロ終了で
  スクリプトごと即終了する」「`set -u`と組み合わせるとbash 5.2.15で
  `unbound variable`になる場合がある」という別の落とし穴があるため、
  ファイル経由での受け渡し自体は妥当な回避策である。
- **裸の`exec`にリダイレクトを付けると、そのリダイレクトは現在のシェルへ
  恒久的に適用される**（`(...)`のようなサブシェルを介さない限り）。例えば
  `exec 3>&- 3<&- 2>/dev/null || true`と書くと、この`2>/dev/null`はfdクローズ
  自体の警告を消すだけのつもりが、**スクリプト全体の以後のstderrを永久に
  `/dev/null`へリダイレクトしてしまう**（`FAIL`メッセージも、被テスト
  プロセスがクラッシュ時に吐く内容も、一切表示されなくなる）。
  **対処: `{ exec 3>&- 3<&-; } 2>/dev/null || true`とブレースでグループ化し、
  リダイレクトの適用範囲をfdクローズ自体に限定する。** 裸の`exec ... N>...`は
  シェル自身の設定を恒久的に書き換えるためのものであり、「このコマンドだけ
  リダイレクトを変えたい」という意図がある場合は、単一コマンドであっても必ず
  `{ }`かサブシェル`( )`で明示的に囲むこと。
- ~~REPLのプロンプトは行末に改行を持たないため、標準入力が端末でない状態では
  プロンプト文字列とクエリ結果が同じ行に連結される。~~ **フェーズ③Step 1で
  解消済み。** 標準入力が端末でない場合はREPLモードであってもプロンプト・
  継続プロンプト・バナーを一切出さない`isInteractive`判定を導入した
  （仕様書§13）。以後、非対話実行時の`SELECT 7;`の結果は`SanDBox> 7`ではなく
  `7`単体の行になるため、`tests/e2e.sh`のアサーションは`grep -qx`（完全一致）
  を使える箇所を積極的に使うこと（1行で完結する値の検証には`-x`、複数行に
  またがるブロックの部分一致検証には引き続き`grep -q`を使う）。
- **`.overwrite`直後に退避ファイル（`.san-db-ox.old`）が消えていることを
  アサーションしてはいけない。** Windowsではそのプロセス自身が実行中の間、
  退避ファイルはロックされたままで削除できない（正常な仕様、仕様書§11）。
  削除されるのは**次にそのバイナリを起動した時**（`OpenSelf()`のベスト
  エフォート削除）。e2eで検証する場合は、`.overwrite`の直後ではなく、
  **その後もう一度バイナリを起動した後**に退避ファイルの不在を確認すること
  （Linuxではどのタイミングで確認しても即座に消えているため気づきにくい）。
- **`.snapshot`がFILENAMEを省略した場合のデフォルト名（実行中バイナリ名が
  ベース、naming.md）は、CWDが実行ファイルの置き場所と同じであれば
  「自分自身のパスへの`.snapshot`」に必然的になる。** この場合、
  `engine.Snapshot`は内部で`.overwrite`と同じ退避方式に自動的に切り替わる
  （仕様書§11）。e2eでこのケースを検証する際、**「ファイルが存在する」
  ことだけを確認するアサーションは弱すぎる**——書き込みが実際には失敗して
  古い内容のまま残っていても素通りしてしまう。書き込み前後で区別できる
  データ（例: 直前に1行INSERTしておく）を仕込み、**再起動後にその新しい
  データが実際に読めることまで確認する**こと。

> **出所:** 前身プロジェクト **ExecDB** の開発中に発生した事象。ExecDBは
> 本体がTCP/UNIXソケットで待ち受ける外部I/Fを持っていたため踏んだが、
> SanDBoxでもsocat経由の待受や`--serve-stdio`の子プロセスを手動起動して
> 調査する場面で同じことが起こりうる。

`tests/e2e.sh`側の孤児プロセス処理（PID配列＋`trap cleanup EXIT`）が正しくても、
**`make test`を経由せず手動でバックグラウンドプロセス（socat経由の待受、
`--serve-stdio`の子プロセス等）を起動して実機確認した際、作業後に`kill`し
忘れると、次回のテスト実行がサイレントに壊れる。** 特にポートやUNIXソケットを
使うテストでは、孤児が先に同じアドレスを掴んでいると、新しく起動したはずの
（実際にはbindに失敗して即終了した）プロセスではなく、**古い孤児プロセスに
対してテストが実行されてしまう**。孤児側は前回までのデータが残ったままなので、
「固定値を1回だけINSERTして件数を確認する」類のテストが、蓄積した重複行の
せいで謎の失敗をする——テストコード自体は正しいため、原因の見当がつきにくい。

**対処:** 手動でバックグラウンドプロセスを起動して調査したら、作業の最後に
必ず`kill`する。テストが原因不明に失敗する・途中で唐突に止まる場合は、まず
`ps aux | grep san-db-ox`（該当ポートを使うなら`ss -ltnp | grep <port>`）で
孤児プロセスの有無を確認すること。

## GitHub Actions CI設定時の落とし穴

> **出所:** 前身プロジェクト **ExecDB** で、初回push後にCI上でのみ顕在化した
> 不具合。手元（Linux）では再現しない種類の問題であり、SanDBoxでも同じ構成
> （マルチプラットフォームのホステッドランナー）を採る以上、そのまま当てはまる。
> あらかじめ対処しておくとよい。

- **`Makefile`やシェルスクリプトで`/dev/stderr`等のUnix固有デバイスパスに
  依存する記述は、Windowsランナー（Git Bash/MSYS環境）で壊れる。** 例:
  `gofmt -s -l . | tee /dev/stderr`は`tee: /dev/stderr: No such file or
  directory`で失敗する。`tee`を使わず、出力を変数に受けてから
  `echo "$var" 1>&2`のように標準の重定向だけで書き直すこと。
- **Windowsランナーのgit checkoutはデフォルトで`core.autocrlf=true`相当の
  挙動になりうるため、`.go`ファイルがCRLFで展開され、`gofmt -l`（LF前提）が
  全ファイルを「未整形」と誤検知する恐れがある。** リポジトリルートに
  `.gitattributes`（`* text=auto eol=lf`）を置き、チェックアウト時の改行
  コードをプラットフォームによらずLFに固定すること。**最初のpush前に置く。**
- **GitHub Actionsの`uses: owner/repo@TAG`は、実際のリリースタグ名と
  厳密に一致しないと`Unable to resolve action`で失敗する。** 特に`v`
  プレフィックスの有無を見落としやすい。ワークフローに書く前に
  `curl -sf https://api.github.com/repos/<owner>/<repo>/releases/latest`等で
  `tag_name`の正確な文字列を確認すること。
- **Windowsには`chmod`による実行ビットという概念が無い。** ファイルの
  実行可能性は拡張子（`.exe`/`.bat`/`.cmd`等）でのみ判定されるため、
  `os.Chmod(path, 0o755)`を呼んでも、その後`os.Stat(path).Mode().Perm()`
  で実行ビット（`0o100`等）を確認するテストはWindowsで失敗する
  （常に`-rw-rw-rw-`相当になる）。「拡張子を含まないファイル名に対して
  chmodで実行可能にした」という状態をテストで検証したい場合は、
  `runtime.GOOS != "windows"`でそのアサーションだけガードすること
  （`GOOS=windows`への単純なクロスビルドではこの種の実行時アサーション
  の誤りは検出できず、実際にWindowsランナー上で`go test`を走らせて
  初めて発覚する）。

## `windows-latest`にGNU Makeがプリインストールされていない

`ubuntu-latest`/`macos-latest`には`make`が標準で入っているが、
**`windows-latest`には入っていない。** `test.yml`で`make check`/`make test`を
共通コマンドとして3OS全てで実行したい場合、Windowsのジョブにだけ
`choco install make -y`のステップを追加すること（`runner.os == 'Windows'`で
ガードする）。`make`実行時は`shell: bash`を明示し、Windowsランナーに標準で
入っているGit Bashでレシピ（`$$`によるコマンド置換等）が正しく解釈されるように
すること（既定のシェルはPowerShellであり、Makefileのレシピ構文と噛み合わない）。

## Windowsで「同じファイルを指すパス」を文字列比較だけで判定してはいけない

`os.Executable()`が返すパスと、`os.Getwd()`から組み立てた（別の経路で得た）
パスが、**実際には同じファイルを指していても、文字列としては異なる表現に
なることがある**（例: 一方にだけ短縮8.3形式のパス要素——`RUNNER~1`のような
もの——が含まれる）。`filepath.Abs`＋`filepath.Clean`＋大文字小文字を無視した
比較（`strings.EqualFold`）だけでは、これを「別のファイル」と誤判定する
（`engine.Snapshot`の自己上書き検知で実際に踏んだ。Windows CIで2回連続で
失敗し、2回目でようやくこの根本原因に気づいた——1回目の失敗は`rename`が
「アクセスが拒否されました」で落ちる現象だけを見て、文字列比較の実装自体が
間違っている可能性を疑わなかった）。

**対処: 両方のパスが実在するなら`os.SameFile`（`os.Stat`した`os.FileInfo`
同士を渡す）でOSレベルのファイル同一性を判定すること。** Windowsでは
ボリューム＋ファイルインデックス、Unix系ではデバイス＋inodeで比較され、
パスの綴り方の違いに左右されない。まだ存在しないパス（比較対象の一方が
これから作られるファイルである場合）に対してのみ、パス文字列の比較へ
フォールバックする。

## Git Bash（MSYS）のパス自動変換は、パイプ経由のテキストには効かない

`tests/e2e.sh`の`$WORK`（`mktemp -d`の結果）は、Windows上のGit Bashでは
MSYS形式（`/tmp/tmp.XXXXXXXX`のようなUnixスタイル）の文字列になる。
**MSYSはこれをネイティブのWindowsプログラムへ`argv`や一部の環境変数として
渡す際に自動的にWindows形式（`C:\...`）へ変換するが、この変換は
`CreateProcess`境界（プロセス起動時）でのみ働く。** SanDBoxのREPLへ
`printf '...' | "$WORK/bin$EXE"`のように**標準入力ごしにテキストとして
`$WORK`ベースの絶対パスを渡すと、この変換の対象外**になる。

**実際に踏んだ症状:** `.snapshot`の保存先パスを`$WORK/raced-snapshot.exe`の
ような形で標準入力に埋め込んだところ、Windows CIで
`open \tmp\tmp.XXXXXXXX\...: The system cannot find the path specified.`
というエラーになった。GoのWindows向けパス解決は、先頭`/`を「カレント
ドライブのルート」と解釈するため（MSYSルートという意味にはならない）、
実際のテンポラリディレクトリ（`C:\Users\...\AppData\Local\Temp\...`）とは
全く別の、存在しない場所を探しに行ってしまう。

**対処は2通りある。**
1. **可能なら絶対パスを埋め込むこと自体を避ける。** 対象プロセスの作業
   ディレクトリを`$WORK`に`cd`させた上で、ベアな相対ファイル名だけを
   標準入力に渡す（`.snapshot`のデフォルト名の検証で既に使っていた手法を
   他のケースにも展開する）。
2. **どうしても絶対パスが必要な場合（`go install`の`GOBIN`のような
   環境変数等）は、`cygpath -w`（Git for Windows同梱）で明示的に
   Windowsネイティブ形式へ変換してから渡すこと。** bash側のファイル
   操作（`cp`/`chmod`/`[ -f ]`等）にはMSYS形式のままの変数を使い続け、
   ネイティブプロセスへ渡す値だけを別変数に変換して分離する
   （同じ変数を使い回すとbash側の操作が壊れる）。

## Windows上の拡張子補完(naming.md)を、生成物のファイル名を直接検証するテストで見落とすと壊れる

`snapshotFilename`（naming.md）は拡張子省略時、実行ファイル出力なら`goos ==
"windows"`でのみ`.exe`を補完する（SQLite出力の`.sqlite`は全OS共通）。
`--snapshot-interval`のユニットテスト（`interval_test.go`）が、生成される
はずのファイル名を`"periodic"`と決め打ちで`os.Stat`していたため、Windows CIで
`.exe`が付いた実際のファイル名（`periodic.exe`）を見つけられずタイムアウトで
失敗した——`stderr`が空（`db.Snapshot`自体は成功していた）という手がかりが、
「一度も保存が実行されていない」という誤った仮説に誘導しやすい失敗の仕方をする。

**対処:** テストが期待するファイル名は決め打ちせず、実装が使っているのと
同じ`snapshotFilename`（や`defaultSnapshotBase`）をテスト側からも呼んで
算出すること。実装とテストの期待値が同じ関数から出てくる限り、OS差分が
新たに増えても構造的にズレなくなる。

## `script`コマンドはLinux(util-linux)とmacOS(BSD)でオプション体系が別物

`tests/e2e.sh`のCtrl+C検証（PTY必須、`interrupt.go`参照）が使う`script`
コマンドは、同名でもOSによって実装が違う。

- **util-linux（Linux）**: `-c command`でコマンド文字列を1つ、`-e`で子
  プロセスの終了コードをscript自身の終了コードとして返せる。2.35以降、
  `file [command...]`という位置引数形式は廃止されている。
- **BSD（macOS）**: `-c`/`-e`のどちらも無い。構文は`script [-akq] [file
  [command ...]]`——`command`とその引数をfileの後にそのまま列挙する。
  終了コードを返す手段がない。

**両対応にする際、`sh -c`のexec最適化に足をすくわれる。** 単一の外部
コマンドだけを渡す一行（例: `"$interrupt" -q`）なら、シェルはforkせず
execで自分自身を置き換える（tail call最適化）ため、SIGINTはptyの
フォアグラウンドプロセスグループの中でそのコマンドだけに届く。しかし
終了コードを`STATUS_FILE`へ書き出すために2行目（`echo $? >file`）を
足した瞬間、この最適化が効かなくなり、**そのシェル自身がフォアグラウンド
プロセスグループの一員として生き残る**。Ctrl+Cで送られるSIGINTはそのシェル
にも配送され、デフォルトの処理（非対話シェルは即終了）でシェルごと死ぬため、
テスト対象プロセスがまだSIGINTを処理中でも`echo $? >file`に到達できず、
「終了コードを記録するはずのファイルが存在しない」という失敗になる
（`strace -f`で、Ctrl+Cのバイトから生成されたSIGINTがラッパーシェルの
PIDにも配送され、そのシェルが`+++ killed by SIGINT +++`で死んでいることを
実際に確認した）。

**対処:** 終了コードを記録する複数行ラッパースクリプトの先頭で
`trap '' INT`し、ラッパーシェル自身へのSIGINTを無視すること。テスト対象
プロセス（子プロセスとして実行される）は親のtrapを継承しないので、自分の
SIGINTハンドラを普通に使い続けられる。OS分岐が必要なのは`script`自体の
呼び出し構文だけにし、終了コードの記録方法（trapしたラッパースクリプト
経由）はOSを問わず共通化するのが安全（`tests/e2e.sh`のCtrl+Cブロック参照）。

## macOSの標準環境には`timeout`コマンドが無い

GNU coreutilsの`timeout`はLinuxディストリビューションには標準で入っているが、
**macOSのベースシステムには存在しない。** Homebrewの`coreutils`パッケージ
経由で入る場合も、既存の`timeout`（が無い）と衝突しないよう`gtimeout`という
別名でインストールされる。`macos-latest`のGitHub Actionsランナーに`coreutils`
がプリインストールされているとは限らないため、**`gtimeout`の存在も保証
されない。**

`tests/e2e.sh`のCtrl+C検証で`timeout 10 script ...`を無条件に呼んだところ、
macOS CIで`Error 127`（command not found）を起こした。**`command -v`で
`timeout`→`gtimeout`の順に存在確認し、両方無ければタイムアウト無しで実行に
フォールバックするヘルパー関数（`run_with_timeout`）を経由すること。**
タイムアウト無しで実行することが安全な理由: CIジョブ自体に上位のタイムアウトが
必ず設定されているため、ここでのタイムアウト消失は「検出が少し遅れる」程度で
CIを止め切れなくなるわけではない（テスト自体を無限に止める`fail()`ではなく、
あくまで安全網）。

**変数展開での分岐は罠になる。** `TIMEOUT_BIN=""; $TIMEOUT_BIN 10 cmd`のように
空文字列になりうる変数をコマンド名の位置に置くと、単語分割で消えて
`10 cmd`という別のコマンドラインに化ける（`10: command not found`）。
`if`で存在確認してから呼び出し全体を出し分ける関数にする方が確実
（`tests/e2e.sh`の`run_with_timeout`参照）。

## `-race` の運用方針

`engine`が`Session`（専有コネクション）を複数の独立したクライアントに配る
設計になっているため、並行性のバグは`-race`で継続的に検出したい。一方で
`-race`はcgo（Cコンパイラ）を要求するため、`binary-size.md`・
`directory-structure.md`が前提とする「本体はpure Go・`CGO_ENABLED=0`」という
方針とは別枠で扱う。

- **`make race`（`CGO_ENABLED=1 go test -race -count=1 ./...`）を用意し、
  `make check`には含めない。** `check`はコミット前に素早く回す用途
  （`PostToolUse`フックからも自動実行される）なので、cgoビルド分の速度低下
  ・追加の外部依存（Cコンパイラ）を持ち込まない。
- **GitHub Actionsでは`race`を`check`とは別ジョブにし、
  `ubuntu-latest`/`macos-latest`限定で実行する。** ubuntu/macosのホステッド
  ランナーにはgcc/clangがプリインストール済みだが、**windows-latestには
  MinGW等のCコンパイラが標準では入っていない**ため対象から外す。
- 開発者の手元環境（devcontainer、`CGO_ENABLED=0`）で`-race`を試す場合は、
  そのコマンド呼び出しだけ`CGO_ENABLED=1`を明示的に指定する必要がある
  （`make race`は自動でこれを行う）。手元にgcc等のCコンパイラが入っている
  ことが前提（devcontainerには標準で入れておく）。

## `gofmt -s` のdocコメント整形時の落とし穴

> **出所:** 前身プロジェクト **ExecDB** の開発中、Go 1.26.7 の`gofmt -s`で
> 発覚した挙動。Goツールチェーン側の仕様であり、SanDBoxでも同様に起こる。

`gofmt -s`は、**関数/型/変数などの宣言に直接紐づくdocコメント**
（`go/doc/comment`パッケージによる整形の対象）の中に、隣接する`''`
（シングルクォート2つ）があると、これを単一の右巻きクォート文字`”`
（U+201D）へ静かに書き換える。

```go
// TEXT single-quoted with '' escaping, BLOB as X'..' hex
```

のようなコメントは、`gofmt -s -w`を通すと

```go
// TEXT single-quoted with ” escaping, BLOB as X'..' hex
```

になり、**SQLのエスケープ規則（`''`で1つの`'`を表す）を説明する意味が
壊れる**。`fmt-check`（`make check`が使う）は`gofmt -s -l .`なので、CIでも
同じ書き換えが必要になる（＝書き換え後の形でコミットしないと`fmt-check`が
失敗する）。

- **関数内の通常のインラインコメント（宣言に紐づかないもの）には影響しない。**
  doc comment整形の対象外だから。
- **回避策: docコメント内で`''`を隣接させない。** 「シングルクォートを2つ
  並べて1つの`'`を表す」のような言葉で説明する。
- SQLの`''`エスケープ規則や、その他「同じ記号を2つ並べる」表記全般
  （シェルの`''`等）をdocコメントで説明する際は、書いた直後に
  `gofmt -s -d <file>`（または`make fmt`→`git diff`）で意図しない書き換えが
  起きていないか確認する習慣をつけるとよい。

## `coproc`の書き込み側fdを閉じる前に、相手プロセスを先に終了させてはいけない

`tests/e2e.sh`のstdioプロトコルe2e（`--serve-stdio`）で、`coproc`（bash組み込み）
経由でリクエスト/レスポンスをやり取りした後、`{"op":"close"}`を送って相手
プロセスを正常終了させてから`exec {NAME[1]}>&-`（書き込み側fdを閉じる）と
`wait "$NAME_PID"`を呼んだところ、**`NAME[1]: ambiguous redirect`**で失敗した。

**原因:** bashは`coproc`の子プロセスが（`wait`を呼ぶより前に）自分で終了
したことを検知すると、その時点で`NAME`配列と`NAME_PID`変数を**自動的に
クリアする**（`set -u`下でも「変数が存在しない」エラーにはならず、配列
要素の参照が空文字列に展開される、という中間的な状態になる——`exec
{NAME[1]}>&-`のようにfd指定の文脈で空文字列に展開されると「ambiguous
redirect」になる）。`{"op":"close"}`（または`overwrite`）はSanDBox側の
プロセスをその応答直後に終了させる仕様（仕様書§4, §7）のため、応答を
読み終えた時点で子プロセスは既に終了しており、bash側の後始末もほぼ
同時に走っている。

**対処:** `close`/`overwrite`の応答を受け取った後は、`exec {NAME[1]}>&-`・
`wait "$NAME_PID"`を呼ばないこと。子プロセスは既に終了しており、bash側の
fd・PID変数の後始末も自動的に終わっているため、明示的な後始末は不要かつ
有害（このタイミングでは既にエラーになる）。**逆に、`close`/`overwrite`を
送らずにこちらから対話を終える場合**（`docs/usage/stdio-protocol_ja.md`の
シェル例のように、stdinのクローズで終了させる場合）は、相手はまだ
`exec {NAME[1]}>&-`の時点で生きて応答待ちをしているため、この配列・変数は
まだ有効であり、`exec {NAME[1]}>&-` → `wait "$NAME_PID"`は問題なく機能する
——**どちらの手順を踏むかは、相手をどう終了させたかで変わる**、という
点を区別すること。

## `tests/docs.sh`（ドキュメント例の実測検証、フェーズ⑤で新設）

CLAUDE.md「実際にビルドしたバイナリへ流し込んで実測検証したものをそのまま
載せる」という方針を、手動確認だけに頼らず機械的に担保するため、`docs/`配下
（`docs/spec/`・`docs/usage/`・`docs/examples/`・`docs/tour/`）とルート
`README.md`/`README_ja.md`に対して`<!-- verify -->`マーカーで印を付けた
コードブロックを実行し、記載した出力と実際の出力を比較する。`make test`
から`tests/e2e.sh`の後に実行される。

**設計上のポイント:**

- **オプトイン方式。** マーカーが無いブロックは一切実行しない。socat・
  Docker・ダウンロード手順のように実行できない/すべきでない例は印を
  付けずに残せる。
- **1ファイル＝1つの一時ディレクトリ**で、ファイル内の検証ブロックを
  文書順に実行する。`.snapshot`した次のブロックでその生成物を起動する、
  といった章をまたぐ状態の積み上げがそのまま書ける。ファイルをまたいだ
  共有は無い。
- **正規化は2つの「関心事」だけ**（それ以外は完全一致を要求する）:
  1. バージョン文字列（`SanDBox <token>`という形と、stdioのhello行の
     生JSON`"version":"<token>"`という形の**両方**を1つの関心事として
     正規化する。ローカルビルドは`dev`または`go build`時のVCS疑似
     バージョンになるが、ドキュメントの例はリリース時の`v0.1.0`表記で
     書くため、ここが食い違う。stdioの`inspect` opが返す`version`
     （フッターのフォーマットバージョン、整数）は別物なので、この
     正規化パターン（クォートされた文字列値のみを対象にする）では
     触れない設計にしている）
  2. `_YYYYMMDDHHMMSS`というタイムスタンプ付与パターン
- **Linux/macOSのみで実行し、Windowsではskipする。** `tests/e2e.sh`が
  既に踏んでいるMSYS特有のパス自動変換の罠（パイプ経由のテキストには
  効かない）をドキュメント検証にまで持ち込まないため。Windows向けの
  導入手順は散文として書き、検証対象にしない。
- **`csv`モードの出力は検証対象にしない。** 行末がCRLFであり、Markdown
  ソース中に生の`\r`を埋め込むと編集時に消えたり見た目が崩れたりする
  ため。実際のCRLF挙動は`tests/e2e.sh`側で担保する。

**実装中に発見した罠（`docs.sh`自体の実装、および記載内容の実測時）:**

- **複数行にまたがるコマンド（バックスラッシュ継続）は非対応。** パーサーは
  `$ `で始まる1行だけをコマンドとして扱うため、ドキュメント側のシェル例は
  1行にまとめて書く必要がある（複数行に分けたい場合は、後述のheredoc対応を
  使う）。
- **heredocは対応済み。** `<<'EOF'`のようなヒアドキュメント開始をコマンド行
  の末尾から検出し、終端の区切り行が現れるまでの行をすべてコマンドの一部
  として扱う（バックリファレンスに頼らない簡易検出のため、クォート文字の
  対応関係までは厳密にチェックしない）。stdioプロトコルの例のような
  「複数行のJSONをヒアドキュメントで流し込む」形の検証に使う。
- **`.mode json`の実際の出力は`{"columns":[...],"rows":[[...]]}`形式**
  （キーはGoのマップの仕様でアルファベット順）であり、`[{"col":val}]`の
  ような直感的な形ではない。ドキュメントの例を書く際に思い込みで書くと
  実測で必ず落ちるので、迷ったら先に実バイナリへ流し込んで確認すること。
- **`.load`/`.import`は確認メッセージを`r.out`へ出力する**
  （`Loaded data from <file>`・`Inserted N rows into "<table>"`）。
  ドキュメントの期待出力にこれを含め忘れると、コマンド自体は成功して
  いても比較で落ちる。
