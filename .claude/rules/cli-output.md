# CLI出力

## 言語

REPLのメッセージ、エラーメッセージ、`--help`、ログ出力等、CLIが出力する文字列は
**英語**とする。国際的なOSSとしての公開・利用を想定しているため。

（この対話・チャット上でのコミュニケーションは日本語で行うが、コード・コメント・
CLI出力は英語で書くこと。両者を混同しないこと。）

## 出力スタイル（SQLite CLIを参考にする）

SanDBoxのREPLコマンド体系は SQLite CLI（`sqlite3`）を踏襲している
（仕様書§3参照）。コマンド名だけでなく、**実際の出力内容・フォーマットも
`sqlite3` を参考にする**とよい。例えば `.tables` の一覧表示の並び方、
`.schema` の出力形式、クエリ結果を表示する際の列揃え・区切り方など、迷ったら
`sqlite3` コマンドの挙動を確認し、大きく外れない出力にすること。独自の書式を
新たに考案する前に、まず本家の出力を確認する。

**色付け・罫線・TUI等の装飾ライブラリは導入しない。** `sqlite3` 自身も装飾を
最小限に抑えたプレーンテキスト出力であり、CI/CDでのパイプ処理・スクリプト
利用（仕様書§9のユースケース1等）との相性を優先する。また `fatih/color` 等の
軽量なものはともかく、`bubbletea` 等のTUIフレームワークは依存関係を含めて
バイナリサイズを増大させ、「単一バイナリ完結・軽量」というコアコンセプト
（§1）と衝突するため、標準出力の範囲で完結させること（実行ファイルサイズ
全般の方針は `binary-size.md` 参照）。

## モードごとの出力先の使い分け

SanDBoxは4つの動作モードを持つ（仕様書§2）。stdoutへ何を出すかがモードごとに
異なるので、実装時に取り違えないこと。

| モード | stdout | バナー | プロンプト |
| :--- | :--- | :--- | :--- |
| REPL（対話端末） | クエリ結果（`.mode`に従う） | 出す | 出す |
| REPL（非対話、標準入力が端末でない） | クエリ結果（`.mode`に従う） | **出さない** | **出さない** |
| バッチ実行（`-c` / stdin） | クエリ結果（`.mode`に従う） | 出さない | 出さない |
| stdioプロトコル（`--serve-stdio`） | **JSON Lines のみ** | 出さない | 出さない |
| ライブラリ | ─（呼び出し元の責任） | ─ | ─ |

**stdioモードのstdoutは、プロトコルの応答行以外を一切含んではならない。**
デバッグ用の`fmt.Println`を1つ紛れ込ませただけでクライアントのパースが壊れる。
診断出力は必ずstderrへ。

**REPLモードでも、標準入力が対話端末でなければプロンプト・継続プロンプト・
バナーを一切出さない**（`isInteractive`での判定。仕様書§13、フェーズ③で確定）。
`-q`/`--quiet`とは独立した判断軸である——`-q`はユーザーの明示指定、こちらは
実行環境（端末かどうか）から自動的に決まる。同じ`isInteractive`判定を
Ctrl+Cハンドラの登録可否にも使う（後述）。

### REPL・バッチ実行内でのstdout/stderrの分担

**プロンプト・バナー・`.snapshot`/`.overwrite`等の確認メッセージ
（`Wrote ...`、`Overwrite ok, exiting.`等）はstdoutへ出す。** sqlite3 CLI
準拠——クエリ結果と同じ経路に載せることで、対話時に「今何が起きたか」を
一続きの出力として見られる。**エラー（`Error: ...`）・警告
（`Warning: ...`）はstderrへ出す。** この分担は非対話時にも変わらない
（バナー・プロンプト自体が出なくなるだけで、確認メッセージの出力先は
変わらない）。

## 出力モード（`.mode` / `.headers`）

`.mode`は`list`（既定）/`column`/`csv`/`json`/`line`の5種のみを採用する。
`quote`/`insert`/`tabs`/`markdown`/`box`/`html`等の装飾系モードは、上記
「出力スタイル」節の方針（装飾を最小限に、CI/CDでのパイプ処理を優先）に
より不採用（増やす場合はまず`san-db-ox_spec_ja.md`§3を更新してから着手する）。

- **`list`**: `|`区切り・ヘッダなし・NULLは空文字列。
- **`column`**: 列幅を値の最大幅（ヘッダ含む）に揃えて左詰め。**`.mode column`へ
  切り替えると`sqlite3`同様`.headers`が自動でonになる**（その後`.headers off`
  で個別に無効化できる）。ヘッダ行の下に`-`の下線行を出す。
- **`csv`**: RFC 4180。**行末は`\r\n`（CRLF）**——`sqlite3`の`.mode csv`と同じ
  （`list`等の他モードはLFのまま。CSVだけCRLFにするのはRFC 4180・多くの
  CSVパーサの慣習に合わせるため）。
- **`json`**: 下記「JSONにおける値の表現」に従う。`.headers`の値に関わらず
  常に列名（`columns`）を含む。
- **`line`**: 1列1行の`  name = value`形式（列名は右詰めで`=`の位置を揃える）、
  行の間に空行。`.headers`の値に関わらず常に列名を含む（形式そのものに
  列名が組み込まれているため）。

## JSONにおける値の表現（`.mode json` と stdioプロトコルで共通）

**`.mode json` と stdioプロトコル（仕様書§7）は同一の規則を使う。**
両者で異なる表現を持たせないこと。実装も1箇所に集約する。

| SQLiteの値 | JSON表現 | 例 |
| :--- | :--- | :--- |
| NULL | `null` | `null` |
| INTEGER | 数値 | `42` |
| REAL | 数値（**小数点を必ず付ける**） | `88.0` |
| TEXT | 文字列 | `"alice"` |
| BLOB | **1要素配列**（Base64） | `["iVBORw0KGgo="]` |

- 判別規則は「値がJSONの配列ならBLOB、それ以外はJSONの型がそのままSQLiteの型」。
- BLOBを1要素配列で包むのは、**JSONに対応する型が存在するのがNULL/数値/文字列
  だけで、BLOBだけが存在しない**ため。型情報を別配列（`types`等）で返す方式は
  採らない——UNION等で列内の型が混在したときに嘘になるうえ、値自体が
  自己記述的であれば不要だから。
- **REALは`88`ではなく`88.0`と出力する。** JSONの数値には整数と小数の区別が
  ないため、これを省くとREALがINTEGERとして読まれる。
- 要素数が1でない配列を受け取った場合はプロトコル違反として扱う。
- **既知の制約:** JSONの数値で正確に表現できる整数は 2^53 - 1 まで。SQLiteの
  INTEGER（64bit）の全範囲は表現できず、JavaScript等ではエラーなく値がずれる。
  この割り切りは意図的な決定であり、整数を文字列化する変更は行わないこと
  （仕様書§7の「既知の制約」参照）。
- **REALがNaN/±Infの場合:** `encoding/json` はNaN/Infを渡されるとエラーになる
  ため、`+Inf`は`9e999`・`-Inf`は`-9e999`（デコード時に±Infへ丸まる数値
  リテラル、`sqlite3` CLI準拠）、`NaN`は`null`として出力する（仕様書§7参照）。

値の型判別は、`database/sql`から返る値の実際のGo型を型スイッチで見て行う
（BLOB列は`[]byte`、TEXT列は`string`になるはずだが、**実装時に実測で確認する
こと**）。

## SIGINT（Ctrl+C）ハンドラの登録可否

REPLは、**標準入力が対話端末である場合に限り**Ctrl+C（SIGINT）用の
シグナルハンドラを登録する（`isInteractive`での判定）。パイプ・スクリプト
経由の非対話実行時、およびバッチ実行・stdioモードではハンドラを一切登録せず、
SIGINTの既定動作（即座にプロセスを終了）をそのまま残す。

**理由（前身プロジェクト ExecDB での判断を引き継ぐ）:** 対話時はsqlite3準拠の中断コマンドとして扱いたい（クエリの中断・
入力破棄であり、無条件のプロセス終了ではない。詳細は`san-db-ox_spec_ja.md`§13
参照）が、これを非対話実行にも適用すると、**スクリプトから起動した
SanDBoxをCtrl+Cで止められなくなる**という事故につながる（1回目のCtrl+Cが
「クエリ中断／入力破棄」として吸収されてしまい、スクリプトを止めたい
ユーザーの意図と噛み合わない）。対話/非対話でSIGINTの扱いを意図的に
変えている。

## ログ出力先

- ログ・診断メッセージは**標準エラー出力（stderr）のみ**とする。ログファイルの
  生成・ローテーション等の機構は持たない。
- クエリ結果・プロトコル応答は標準出力（stdout）に出力する。stdout（結果）と
  stderr（ログ・診断）は明確に分離すること。**この分離はstdioプロトコルが
  成立するための前提条件である**（仕様書§0）。
- 永続的なログ保存は、リダイレクトやDocker/systemd等の既存運用基盤に委ねる。
  SanDBox自体はログファイルを生成しない。
- `-q`/`--quiet` で出力自体を抑制できる。

## 起動時バナー

`.status`のような専用コマンドは設けない。代わりに**REPLモードでのみ**、起動時に
バージョン・埋め込みデータの有無・スナップショット名・読み取り専用かどうかを
1度だけバナーとして表示する（`-q`/`--quiet`で抑制可能）。実行中に再確認したい
場合も、この情報が動的に変わることは想定しないため、専用コマンドを別途設けない。
バナーの具体的な表示例は仕様書§13参照。

stdioモードにはバナーが無いため、同じ情報は`inspect` opで取得できるようにする
（仕様書§7）。**バナーと`inspect`は同じ情報源から生成すること**——片方だけ
更新して食い違うのを防ぐ。

## 保存確認プロンプト

`.exit`/`.quit` は、未保存の変更があっても**保存確認のプロンプトを出さず、
即座に終了する**（意図的な設計判断。詳細は仕様書 §3, §4 参照）。CI/CD等の
非対話実行との相性、および「保存は明示操作のみ」という原則を優先しているため、
確認プロンプトを追加する変更は行わないこと。

## 読み取り専用モード（`--read-only` / `-r`）の出力

- 起動バナーに読み取り専用である旨を1行加える（`SanDBox v0.1.0 (read-only)`）。
- **`.help`の出力を差し替え、拒否される操作を一覧に含めない。** 打てないコマンドを
  ヘルプに出したうえで実行時に断る、という二度手間をユーザーに強いない。
- stdioモードでは、拒否した操作に対して`read_only`エラーコードを返す。
- 拒否対象は仕様書§2を参照（書き込みSQL、`.snapshot`、`.overwrite`、`.load`、
  `.snapshot --sqlite`）。
