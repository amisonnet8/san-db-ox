# 🗃️ SanDBox 仕様書

**SanDBox** は、DBエンジンとデータ領域を1つの実行ファイル内に保持する、環境構築不要のポータブルな単一バイナリRDBMSです。

**License:** MIT

>
> * 「今すぐ使う」ための索引的なリファレンスは `docs/usage/` を参照（起動オプション・REPLコマンド・stdioプロトコルの一覧）。
> * テスト方針・開発フェーズ・配布方法・命名規則といった**開発上のルール**は `.claude/rules/` 配下が担当し、本書には含まれない。
> * 各言語向けのクライアントドライバは、別プロジェクト `san-db-ox-clients` が提供する。本書が定めるのは**プロトコルまで**である。
>

## 0. 名称と表記規則

「Sandbox（砂場）」の中に「DB」を埋め込んだ造語である。表記は3段階の優先順位で使い分ける。**上の段が使える場面では必ず上の段を使う。**

| 優先 | 表記 | 使う場面 |
| :--- | :--- | :--- |
| 第1 | `san-db-ox` | 制約が無い全ての場面（リポジトリ名、実行ファイル名、モジュールパス、ソケットパス、イメージ名） |
| 第2 | `san_db_ox` | ハイフンが使えない場面（環境変数、C言語の識別子） |
| 第3 | `sandbox` | 上記2つが長さ等の理由で使えない場面（固定長フィールド） |

| スロット | 正規表記 | 適用段 |
| :--- | :--- | :--- |
| 表示名（バナー・README・本仕様書） | `SanDBox` | ― |
| リポジトリ / Goモジュールパス | `github.com/amisonnet8/san-db-ox` | 第1 |
| 実行ファイル名 | `san-db-ox`（Windows: `san-db-ox.exe`） | 第1 |
| 自己上書き時の退避ファイル | `<path>.san-db-ox.old` | 第1 |
| 環境変数（現時点で該当なし。将来追加する場合） | `SAN_DB_OX_*` | 第2 |
| Cクライアントの識別子 | `san_db_ox_*` | 第2 |
| Goパッケージ名 | `engine` | ― |
| フッターのMagic（8バイト固定） | `SANDBOX1` | 第3（9文字が枠に入らないため） |

**別名（エイリアス）は提供しない。** ユーザーが口頭で「サンドボックス」と呼び、ターミナルで `sandbox` と打ちたくなることは想定されるが、`sandbox` は第3段＝他が使えない場合の代替であり、ユーザーが打つコマンド名として用意することは上記規則に反する。シンボリックリンクやラッパースクリプトの同梱は行わず、READMEでの明示に留める（単一バイナリ完結というコンセプトとも整合する）。

**ハイフンとタイムスタンプ規則:** 実行ファイル名にハイフンが含まれていても、§12「タイムスタンプ付与」の規則（区切りは `_` 固定）とは衝突しない。`san-db-ox_20260901120000.exe` のようになる。実装時、ベース名の照合はハイフンを含む文字列を前提とすること。

**ファイル拡張子は製品名を含めない。** 非実行形式のファイルは素のSQLiteファイルであり（§6）、`.db` / `.sqlite` という既存の慣習に従う。`.san-db-ox` や `.sandbox` のような独自拡張子は用いない。

**「セキュリティサンドボックス」ではない:** 本ソフトウェアは隔離・権限制限・リソース制限を提供しない。§1 の Zero-Auth が示す通り、権限分離の概念自体を持たない。名称から想起されるセキュリティ的な閉じ込め機能とは**一切関係がない**。

**CLI出力言語:** REPLのメッセージ、エラーメッセージ、`--help`、ログ出力等、CLIが出力する文字列は基本的に**英語**とする。国際的なOSSとしての公開・利用を想定するため。

**ログ出力先:** ログ・診断メッセージは**標準エラー出力（stderr）のみ**とし、ログファイルの生成・ローテーション等の機構は持たない。単一バイナリで完結するというコアコンセプトに合わせ、副産物としてのログファイルを生成しない設計とする。クエリ結果・プロトコル応答は標準出力（stdout）に出力するため、両者は常に分離される。**この分離は §7 の stdio プロトコルが成立するための前提条件でもある。** `-q`/`--quiet` で出力自体を抑制することも可能。

## 1. コアコンセプト

* **Data-in-Binary (単一バイナリ完結):** 実行ファイル内にデータ領域を持ち、外部のDBファイルや複雑な環境構築、Docker Volumeマウントを一切不要にします。
* **In-Memory Operations:** 起動時に全データをメモリ上に展開し、すべてのクエリ操作をメモリ速度（超低遅延）で処理します。
* **Snapshot Persistence (別名実行ファイルの出力):** 停止時（または実行中の保存指示）に、メモリ上の最新データを保持した**新しい実行ファイル（別名）**を生成して永続化します。元の実行ファイルを維持することで、安全なスナップショット作成やデータ配布を容易にします。
* **Zero-Auth & Zero-Network:** ユーザー管理、権限、ログインなどの概念を持ちません。**自身ではネットワーク待受を一切行いません。**
* **明示操作による永続化のみ:** データの保存はユーザーの明示的な指示（`.snapshot` / `.overwrite`）でのみ行われます。プロセス停止時の自動保存は**例外なく**行いません（`--snapshot-interval` によるオプトインの定期保存を除く）。

### ネットワークを持たないという選択

SanDBox はネットワークプロトコルを実装しない。認証機構を持たないのは、そもそも外部から到達する経路を製品自身が作らないためである。「弾くロジックを書いて防御する」のではなく「弾く手段が構造的に存在しない」ことによる安全性であり、`net`・`net/http` をimportしないことはコードレベルで検証できる（§10）。

この選択の代償として「バイナリ1つ置けばDBサーバーになる」という形は取れないが、他システムとの結合は次の2つで達成する。

1. **プロセスとして起動され、標準入出力で対話する**（§5・§7）。サブプロセスとパイプを扱える処理系であれば、専用ライブラリなしに任意の言語から結合できる。
2. **素のSQLiteファイルとして読み書きする**（§6）。既存のGUIツール・各言語のsqliteドライバ・pandas等のエコシステムへ、プロトコル実装ゼロで接続できる。

ネットワーク越しに公開したい場合は、`socat` 等の既存ツールでトランスポートを外付けする（§8）。口を開ける判断と責任は運用者側にあり、製品側には残らない。

## 2. インターフェース

SanDBox は4つの動作モードを持つ。**いずれもネットワーク待受を伴わない**（プロセスを起動できる主体＝ローカルのユーザーのみが到達できる）。

| モード | 起動方法 | 用途 | 入出力 |
| :--- | :--- | :--- | :--- |
| **対話式コンソール (REPL)** | 引数なしで起動（デフォルト） | 人間による対話操作 | 端末 |
| **バッチ実行** | `-c "SQL"` / stdin からのスクリプト | CI/CD、シェルスクリプトからの利用 | stdout（`--mode` に従う） |
| **stdio プロトコル** | `--serve-stdio` | 他プログラムからの結合（§7） | stdout（JSON Lines 固定） |
| **ライブラリ** | `engine` パッケージをGoアプリへ組み込み | 内蔵DB層（§10） | Go関数呼び出し |

> 各モードのコマンド・オプション・opの一覧は `docs/usage/` を参照。本書は設計判断とその理由を扱う。

### アクセス制御は持たない

経路や文の種別によるアクセス制限（DDLの拒否等）は実装しない。**すべてのモードで DDL / DML / TCL のすべてが実行できる。**

根拠は、SQLレベルで制限しても防御にならないことにある。いずれのモードもローカルプロセスとして起動される以上、起動できる主体はすでに実行ファイル自体への読み書き権限を持っている。DDLを弾いたところで、その主体はバイナリを直接書き換えることも、別のバイナリを実行することもできる。したがって制限は複雑さを増やすだけで、守るものが無い。

### 唯一の例外: 読み取り専用モード

上記の唯一の例外として、起動時に `--read-only`（`-r`、§12）を指定した場合に限り、書き込みを伴う操作をすべて拒否する。

これは前項と矛盾しない。**経路や文の種別による制限ではなく、プロセス全体の起動時モードだから**である。起動する主体が自分の意思で「このプロセスには書かせない」と宣言するものであり、プロセスの外側にいる誰かに対する防御ではない。主な用途は `socat` による外部公開（§8）で、閲覧用のデモ環境を安全に提供したい場合に使う。

拒否する操作は次の通り。

* 書き込みを伴うSQL（INSERT / UPDATE / DELETE / DDL / トランザクション内の書き込み）。実装は SQLite の `query_only` プラグマに委ねる
* 保存操作（`.snapshot` / `.overwrite`）
* データ置き換え（`.load`）
* **SQLiteファイルの書き出し（`.snapshot --sqlite`）**。DBは変更しないが、サーバー側のファイルシステムへ任意のパスで書き込むため、外部公開時には書き込み操作と同等に危険である
* `--snapshot-interval` との同時指定は使用法エラー（終了コード2）とする

REPLモードでは、`.help` の出力を読み取り専用モード用のものに差し替え、拒否される操作を一覧に含めない。起動バナーにも読み取り専用である旨を表示する（§13）。stdio プロトコルでは、拒否された操作に対して `read_only` エラーコードを返す。

### 同時実行制御 (Concurrency Control)

ロック・トランザクション分離レベル等の同時実行制御は、SanDBox 独自には実装せず、内部SQL互換エンジン（§11参照）が標準で備える機構にそのまま準拠する。

`cmd/san-db-ox` の各モードは、いずれも**同時に1つのクライアントしか持たない**（REPLはプロセス自身が唯一のクライアント、stdioは1プロセス=1セッション、バッチは短命）。したがってアプリ側で複数クライアントの調停が必要になる場面は無い。

複数クライアントが同時に存在しうるのは `engine` をライブラリとして組み込んだホストアプリの場合のみであり、その場合は `DB.Session(ctx)` が返す専有コネクション（内部的には `modernc.org/sqlite` の `memdb` VFS 上で同一インメモリDBを指す別コネクション、§11参照）ごとにSQLite自身の排他制御が働く。`BEGIN`/`COMMIT`/`ROLLBACK` はそのコネクション上でSQL文としてそのまま実行され、ロック衝突時の待機・失敗はSQLite自身のbusy-handler機構（`busy_timeout`）に委ねる——SanDBox が独自にロックやキュー、コネクション間の調停を実装することはない。

なお `engine.DB` がGoレベルで持つ排他制御（`sync.RWMutex`）は、コネクションの差し替えや `Close` などDB自体のライフサイクル・メタデータ（`Info()` が返す情報等）を保護するためのものであり、SQL実行そのものの同時実行制御ではない（両者は明確に別レイヤーであり、上記の原則と矛盾しない）。

## 3. REPL コマンド体系

対話式コンソール(REPL)では、SQL文に加えて `.` で始まる専用制御コマンド(ドットコマンド)を実行できる。コマンド体系は SQLite CLI (`sqlite3`) を踏襲しつつ、SanDBox の単一インメモリDBというコンセプトに合わせて取捨選択する。

**ドットコマンドはバッチ実行モード（§5）でも同様に使える。** stdio プロトコル（§7）では、対応する `op` として提供する。

### 採用する基本コマンド(SQLite踏襲)

| コマンド | 役割 |
| :--- | :--- |
| `.tables` | テーブル一覧表示 |
| `.schema [table]` | CREATE文（スキーマ）表示 |
| `.exit [CODE]` / `.quit [CODE]` | 終了（自動保存は行わない。保存確認のプロンプトも出さず即座に終了する。§4参照。`CODE`省略時は正常終了、指定時はそのコードで即座にプロセスを終了する） |
| `.help` | コマンド一覧表示 |
| `.headers on\|off` | 結果表示にカラム名を出すか |
| `.mode MODE` | 出力形式。`list`（既定、`\|`区切り・ヘッダなし）/`column`（列幅揃え、切替時`.headers`自動on）/`csv`（RFC 4180、CRLF）/`json`（配列）/`line`（1列1行）の5種のみ採用する（`quote`/`insert`/`tabs`/`markdown`/`box`/`html`等の装飾系はCLI出力方針（`.claude/rules/cli-output.md`）により不採用）。JSON出力における値の表現は §7 と共通とする |
| `.import FILE TABLE` | CSVファイルをテーブルへ読み込む。**`.mode`の設定に関わらず常にCSVとして読む**（sqlite3は`.mode`に連動するが、「`.import`は常にCSV」と単純化——意図的な相違）。`TABLE`が存在しなければ1行目を列名として全TEXT列で自動`CREATE`、存在すれば1行目からデータとして扱う。**行ごとのフィールド数が列数と一致しない場合はその行番号を含むエラーで処理全体を中断し、1行も投入しない**（sqlite3は警告のうえ補完/切り捨てして継続するが、シードデータ投入という主用途では黙って歪んだデータが入る方が有害と判断——意図的な相違） |
| `.dump [PATTERN]` | `PATTERN`（SQLのLIKEパターン、省略時は全テーブル）に一致するテーブルのスキーマ・データと、それらに属するindex/view/triggerをSQL文としてダンプする。値のリテラル化はSQLite自身の`quote()`関数に委譲する |

### SanDBox 独自で追加するコマンド

| コマンド | 役割 |
| :--- | :--- |
| `.snapshot [FILENAME] [--sqlite] [--timestamp]` | スナップショット保存（§4, §6, §12参照）。既定では別名の**実行ファイル**を生成する。`--sqlite`指定時は**SQLiteファイル**を生成する。`--timestamp`指定時はファイル名にタイムスタンプを付与 |
| `.overwrite` | 自身の実行ファイルを最新データで上書きし、成功したらプロセスを終了する（§4, §11参照） |
| `.load <FILE>` | 別のSanDBox実行ファイル、**またはSQLiteファイル**からデータのみを取り込み、メモリ上のDB状態を置き換える（ファイルは生成しない。§4, §6参照） |

### 採用しないコマンド

SanDBox は常に単一のインメモリDBのみを扱うシンプルな構成のため、以下のSQLite由来のコマンドは採用しない。

* `.open` / `.databases`（複数DB切り替えの概念が無いため）
* `.backup` / `.restore`（`.snapshot` と役割が重複するため）
* `.session`（変更履歴セッション機能。過剰な機能のため対象外）

## 4. 保存・永続化仕様 (Snapshot Mechanism)

データ保持は**「新しい実行ファイル（別名）の生成」**によって行われます。

* **生成タイミング:**
  * **`.snapshot` コマンドによる明示保存のみ:** 手動指示があった場合にのみスナップショットを生成する。
  * **プロセス停止時の自動保存は行わない:** SIGTERMや、Ctrl+C（SIGINT）が実際にプロセスを終了させた場合（対話モードでのCtrl+Cの詳しい挙動は§13参照。常に即終了するわけではない）、メモリ上のデータは保存されず消える。SanDBox はメモリDBとしての揮発性を前提とし、永続化はユーザーの明示的な操作に一本化することで、停止処理中の書き込み中断による破損リスクや、不要なスナップショットの自動増殖を避ける。
* **ファイル命名規則:**
  * デフォルトでは日時タイムスタンプを付与した実行ファイルを自動生成（例: `san-db-ox_20260831_143000`）。
  * コマンドライン引数や対話コンソールからの指定により、任意のファイル名での出力や既存ファイルへの上書き更新にも対応。
* **スナップショットファイルの管理:** `.snapshot` のたびにエンジン本体＋データのフルコピーが新規生成されるため、実行のたびにファイル数・容量が増加していく。古いスナップショットの整理（削除）は仕様の対象外とし、運用側（ユーザー）の判断に委ねる。

### 自己上書き（`.overwrite`）という例外

`.overwrite` は、`.snapshot` と同じくユーザーの明示操作による保存だが、**保存と同時にプロセスを終了する**点のみが異なる。上記「プロセス停止時の自動保存は行わない」という原則から唯一逸脱する例外操作であり、学習用途・軽量CLIツールとして「編集してそのまま閉じる」という直感的なワークフローを提供するために意図的に許容する。書き込み方式（実行中ファイルへの上書き回避手順）は§11を参照。

**バッチ実行・stdio プロトコルでも実行できる。** バッチ実行では `san-db-ox -c ".overwrite"` が「データを投入して埋め込み、ビルドを完了する」という自動化の用途で有用である。stdio プロトコルでは `overwrite` op として提供し、**応答を1行返してからプロセスを終了する**（`close` op と同じ扱い）。ただし `socat` 経由での使用は避けること（複数の子プロセスが同じパスへ同時に書きに行くため。§8参照）。`--read-only` 指定時は拒否される（§2）。

### 他ファイルからのデータ取り込み（`.load`）

`.load <FILE>` は、**別ファイルに含まれるデータのみ**を取り込み、**今動いているプロセスのメモリ上のDB状態をそのデータで置き換える**コマンドである。ファイルの生成は行わない（メモリ上の状態を変更するだけ）。

**ファイル種別は内容から自動判別する**（§6参照）。取り込めるのは以下の2種類。

1. **SanDBox の実行ファイル**（末尾フッターのMagicで判別）
2. **SQLiteファイル**（先頭16バイトのヘッダ文字列 `SQLite format 3\0` で判別）

主なユースケースは、異なるOS/アーキテクチャ向けにビルドされたSanDBoxファイル間でのデータ移植（例: Linux上で作成したデータを、Windows用の空バイナリへ取り込んでから配布する）、および既存のSQLiteデータベースの取り込み。

* **動作:** ファイルからデータ部分のみを読み出し、SQLiteエンジンへ取り込むことで（内部実装は§11参照）、今動いているプロセスのメモリ上のDB状態を置き換える。今動いているプロセスが元々持っていたデータは**完全に置き換わる**（マージはしない）。
* **ファイルへの反映:** `.load` 自体はファイルを生成しない。取り込んだ状態をファイルとして保存したい場合は、続けて `.snapshot`（別名保存）または `.overwrite`（自己上書き）を実行する。異なるOS向けバイナリへデータを移植する典型的な流れは次の通り: 対象OS向けの空バイナリを起動 → `.load <FILE>` でデータをメモリへ取り込む → `.overwrite` でそのバイナリ自身にデータを書き込む。
* **エンジン部分は変更されない:** `.load` は取り込み元ファイルのエンジン部分を一切参照しない。常に今動いているプロセス自身のエンジンで、データのみを読み込む。異なるOS向けバイナリのエンジン部分を直接取り込むことはできない。
* **既存セッションへの影響:** `.load` はメモリ上のDBを、生きているデータベースへの上書き（§11参照）という形で置き換えるため、その時点で既に開いている他のセッション（`engine.Session`）は接続自体が失われることなく維持され、以降に発行する文からは置き換え後のデータをそのまま参照できる。
* **取り込めないファイル:** SanDBoxの実行ファイルでもSQLiteファイルでもない場合、またはSanDBoxファイルだがデータ長が0の場合はエラーとなり、今動いているプロセスのメモリ上の状態は変更されない。
* **バージョン不一致の扱い:** 取り込み元ファイルのフッター（`Version`フィールド、§11参照。データブロブのフォーマットバージョンであり、SanDBoxというソフトウェア自体のバージョン——例えばGitタグ——とは別の値）が、今動いているプロセスが書き出すフッターの `Version` と異なる場合、警告を表示した上で処理を続行する（拒否はしない）。この警告表示は `cmd/san-db-ox` 側（呼び出し側）の責務であり、`engine` パッケージ自体はログ出力を行わない（§10の責務分担、ライブラリはstderrに書かない）。`engine` は `Inspect(path)` でファイル種別とフッター情報のみを取得するAPIを提供するので、`cmd/san-db-ox` は `.load` 実行前にこれを呼び、不一致を検出したら自分でメッセージを出す。
* **原則との関係:** `.load` も `.snapshot`/`.overwrite` と同様、ユーザーの明示操作によってのみ実行される。自動的に他ファイルのデータを読み込む機構は存在しない。

## 5. 非対話実行モード（バッチ実行）

CI/CD・シェルスクリプト・Makefile 等から SanDBox を「1回叩いて結果を得る」ために、REPLを起動しない実行経路を用意する。sqlite3 CLI の同種の機能を踏襲する。

### 起動形態

| 形態 | 挙動 |
| :--- | :--- |
| `san-db-ox -c "SQL"` | 指定されたSQLを実行して終了。`-c` は複数回指定でき、指定順に実行する |
| `san-db-ox < script.sql` | 標準入力が端末でない場合、stdin全体をSQLスクリプトとして読み、実行して終了 |
| `san-db-ox -c "SQL" < input` | `-c` が指定されている場合、stdinはスクリプトとして読まない（`.import` 等が stdin を使う余地を残す） |

いずれの形態でも、バナーは表示せず（`-q` 相当）、プロンプトも出さない。REPLへは移行しない。

### 実行と出力

* SQL文・ドットコマンドのいずれも実行できる。`.snapshot` / `.load` もそのまま使える。
* 結果は stdout へ、`--mode`（`-m`）に従った形式で出力する。既定は `list`。**スクリプトから機械的に読む場合は `--mode json` を推奨する。**
* ログ・警告・エラーメッセージは stderr へ出力する（§0）。
* **エラー発生時は即座に処理全体を中断する。** 後続のSQL文は実行しない（`.import` の設計思想と揃える。CIで途中の失敗が黙殺されるのを避けるため）。

### 終了コード

| コード | 意味 |
| :--- | :--- |
| `0` | 全ての文が正常に実行された |
| `1` | SQL実行エラー、またはドットコマンドの実行失敗 |
| `2` | 使用法エラー（不正なフラグ、ファイルが開けない等） |

`.exit CODE` / `.quit CODE` で明示的に終了コードを指定した場合は、その値が優先される。

### 定期スナップショットとの関係

`--snapshot-interval`（§12）はバッチ実行モードでは**無効**とする。プロセスが短命であり、意味を持たないため。指定された場合は警告を stderr へ出して無視する。

## 6. SQLite ファイル入出力

### 独自のデータファイル形式は存在しない

SanDBox が扱う非実行形式のファイルは、**素のSQLiteファイルのみ**である。独自のデータファイル形式は定義しない。

これは実装上の必然でもある。§11 で採用する `sqlite3_serialize()` が返すバイト列は、そのデータベースをディスク上のファイルとして書き出した場合と同一のイメージであり、**実行ファイル末尾に埋め込まれる「データブロブ」は、そのままSQLiteファイルの中身そのもの**である。したがって「データブロブを切り出してファイルに書く」ことと「SQLiteファイルとしてエクスポートする」ことは同じ操作になる。

> **実測確認済み（フェーズ①Step 2）:** この同一性（`Serialize()` の出力がそのまま有効なSQLiteファイルとして開けること）は、`modernc.org/sqlite v1.58.0` で実測確認済み。`Serialize()`が返したバイト列を素のファイルへ書き出し、`vfs=memdb`を一切介さない独立した`sql.Open`（`file:`ではなく通常のファイルパスDSN）で開いて`SELECT`が通ることを確認した。先頭16バイトが`SQLite format 3\0`と一致することも確認済み。

この帰結として、扱うファイル形式は次の2種類のみになる。

| 形式 | 判別方法 | 拡張子 | 生成するコマンド |
| :--- | :--- | :--- | :--- |
| SanDBox 実行ファイル | 末尾32バイトのフッターのMagic | なし（Windowsは `.exe`） | `.snapshot` / `.overwrite` |
| SQLiteファイル | 先頭16バイトの `SQLite format 3\0` | `.db` / `.sqlite` | `.snapshot --sqlite` |

### `.snapshot --sqlite <FILE>` — 書き出し

現在のメモリ上のDB状態を、SQLiteデータベースファイルとして書き出す。`.snapshot` は既定で実行ファイルを生成するが、`--sqlite` を付けるとSQLiteファイルを生成する。**出力の形式選択はこのフラグに一本化し、専用の書き出しコマンドは設けない**（入力側の `.load` が1コマンドで両形式を受けるのと対をなす）。

* 書き出されたファイルは、DBeaver / TablePlus / DB Browser for SQLite などのGUIツール、各言語の標準的なsqliteドライバ、`sqlite3` CLI、pandas 等から**そのまま開ける**。
* 実装は §11 のSQLite標準オンラインBackup API（`modernc.org/sqlite` の `NewBackup`）を、コピー先としてファイルDBに向けて呼ぶ。`Serialize()` の出力を直接書くことも可能だが、Backup API は書き込みトランザクションとの一貫性を保証するため、そちらを採る。
* 書き込みは同一ディレクトリの一時ファイルへ書いてから `rename` するアトミックな方式を採る（§11のスナップショット書き込みと同じ）。
* 既存ファイルが存在する場合は上書きする。
* **拡張子が省略された場合は `.sqlite` を補完する。** Windowsにおける `.exe` の補完（§12）は `--sqlite` 指定時には行わない（実行ファイルではないため）。
* `--timestamp` と併用できる（§12）。
* `.overwrite` には `--sqlite` を適用できない（自分自身をSQLiteファイルにすると実行できなくなるため）。

### `.load <FILE>` — 取り込み

§4 の通り、`.load` はファイル内容から種別を自動判別する。判別は以下の順で行う。

1. ファイル先頭16バイトが `SQLite format 3\0` であれば**SQLiteファイル**として扱う
2. ファイル末尾32バイトのフッターにMagicが見つかれば**SanDBoxの実行ファイル**として扱う
3. いずれにも該当しなければエラー（メモリ上の状態は変更しない）

SQLiteファイルを取り込む場合も、SanDBoxファイルの場合と同様、Backup API で「生きている」インメモリDBへコピーする形を取るため、既存のセッションは接続を失わない。

### 既存エコシステムとの接続

`.snapshot --sqlite` は、ネットワークプロトコルを実装せずに既存のツール資産へ接続するための主要な経路である。GUIクライアント・BIツール・データ分析ライブラリ等、SQLiteを読める全てのソフトウェアが、そのまま SanDBox のデータの閲覧手段になる。プロトコル互換性の維持コストを一切払わずに済む点で、独自プロトコルやワイヤープロトコル互換実装より有利である。

ライブに接続して読み書きする必要がある場合のみ、§7 の stdio プロトコルを用いる。

## 7. stdio プロトコル（外部連携）

他のプログラムから SanDBox を利用するための仕掛け。**SanDBox を子プロセスとして起動し、標準入出力で対話する。**

ネットワークを経由しないため、§1 の Zero-Network・§10 の設計原則を保ったまま、任意の言語から結合できる。C、Python、Ruby、Node.js、PHP、Rust など、サブプロセスとパイプを扱える処理系であれば**専用ライブラリなしで直接繋がる**（各言語向けのクライアントドライバは、この契約の上に乗る薄いラッパーとして別プロジェクトで提供する。本節末尾を参照）。

### 起動と基本フロー

```
san-db-ox --serve-stdio
```

* バナー・プロンプトは一切出さない。REPLへは移行しない。
* **stdout は本プロトコルの応答専用**とする。ログ・診断は stderr のみ（§0）。
* **セッションの寿命＝プロセスの寿命。** トランザクションはプロセス内で自然に維持される。1つの `engine.Session` を保持し続ける。
* stdin が EOF に達したらプロセスを終了する（保存は行わない。§4の原則通り）。

### メッセージ形式

**行区切りJSON（JSON Lines）** を採用する。1行＝1メッセージ。長さプレフィックス方式より実装が簡単で、あらゆる言語で「行を読む」だけで扱えるため。

リクエスト（クライアント → SanDBox）:

```json
{"op":"query","sql":"SELECT id, name FROM users WHERE id = ?","params":[1]}
```

レスポンス（SanDBox → クライアント）:

```json
{"ok":true,"columns":["id","name"],"rows":[[1,"alice"]]}
```

* リクエストに `id` フィールドを含めた場合、対応するレスポンスにそのまま echo back する（省略可）。**応答は常にリクエストと同じ順序で返すため、`id` が無くても対応付けは可能**である。
* リクエストが不正なJSONである場合も、エラーレスポンスを1行返して処理を継続する（接続は切らない）。

### op 一覧

| op | パラメータ | 応答 |
| :--- | :--- | :--- |
| `query` | `sql`, `params` | `columns`, `rows` |
| `exec` | `sql`, `params` | `rows_affected`, `last_insert_id` |
| `snapshot` | `filename`(省略可), `sqlite`(bool, 省略可), `timestamp`(bool, 省略可) | `path`（生成されたファイルのパス） |
| `load` | `path` | `─` |
| `inspect` | ─ | 自プロセスの状態（下記） |
| `tables` | ─ | テーブル名の配列 |
| `schema` | `table`(省略可) | CREATE文 |
| `overwrite` | ─ | 自身の実行ファイルを上書きし、**応答を1行返してからプロセスを終了する**（§4） |
| `close` | ─ | 応答後にプロセスを正常終了する |

`BEGIN` / `COMMIT` / `ROLLBACK` は専用の op を設けず、`exec` でそのまま送る。DDLも `exec` で実行できる（§2、アクセス制御は持たない）。

`query` は結果セットの全行を1つのレスポンスに含めて返す。行を逐次取得するカーソル機構は持たない。

**`inspect` は自プロセスの状態のみを返す。** REPLモードでは起動バナー（§13）が同じ情報を提示するが、stdioモードにはバナーが無いため、接続したドライバがプロセスの状態を知る唯一の手段となる。

```json
{"op":"inspect"}
→ {"ok":true,"has_data":true,"version":1,"data_length":1048576,"source":"mydb_20260901120000","read_only":false}
```

| フィールド | 内容 |
| :--- | :--- |
| `has_data` | 起動時にデータが埋め込まれていたか（`false` なら空のバイナリから起動した） |
| `version` | フッターのフォーマットバージョン（§11）。`has_data` が `false` のときは `null` |
| `data_length` | 起動時に読み込んだデータブロブの長さ（バイト）。同上 |
| `source` | 起動した実行ファイルのファイル名 |
| `read_only` | `--read-only` で起動しているか。書き込みを試す前に判定できる |

**任意のパスを検査する機能は提供しない。** `engine.Inspect(path)` は `.load` 実行前のバージョン不一致警告（§4）のために内部で使うが、これを op として露出させると、外部公開時（§8）にサーバー側のファイルシステムを探る手段になるため。`.load` できるかどうかは `load` を実行してエラーを見れば分かる。

### エラー応答

```json
{"ok":false,"error":{"code":"sqlite_error","message":"no such table: users"}}
```

* `code` は簡略化した識別子（`sqlite_error` / `bad_request` / `io_error` / `unsupported_op` 等）とし、SQLSTATE のような詳細な体系は持たない。
* エラーが発生しても**プロセスは終了しない**。クライアントが続けて別のリクエストを送れる。バッチ実行（§5）が即中断するのと対照的だが、これはセッションが継続する対話的な経路であるため。

### 値のJSON表現

**JSONの型をそのまま使い、JSONに対応する型が存在しないBLOBのみを1要素配列で包む。**

| SQLiteの値 | JSON表現 | 例 |
| :--- | :--- | :--- |
| NULL | `null` | `null` |
| INTEGER | 数値 | `42` |
| REAL | 数値 | `88.5` |
| TEXT | 文字列 | `"alice"` |
| BLOB | 1要素配列 | `["iVBORw0KGgo="]` |

判別規則は1行で書ける。**値がJSONの配列ならBLOB、それ以外はJSONの型がそのままSQLiteの型である。**

```json
{"ok":true,"columns":["id","name","score","avatar","note"],"rows":[[1,"alice",88.5,["iVBORw0KGgo="],null]]}
```

* BLOBの中身は **Base64**（RFC 4648 標準アルファベット、パディングあり、改行なし）でエンコードする。空のBLOBは `[""]`。
* **要素数が1でない配列はプロトコル違反**とする（`bad_request` を返す）。
* **`params` でも同じ表現を受け付ける。** 読み出した値をそのまま書き戻せるよう、往復の対称性を保つ。
  ```json
  {"op":"exec","sql":"INSERT INTO profiles VALUES (?, ?)","params":[1,["iVBORw0KGgo="]]}
  ```
* **REALは必ず小数点を付けて出力する**（`88` ではなく `88.0`）。JSONの数値には整数と小数の区別がないため、これを省くとREALがINTEGERとして読まれる。ただし完全ではない（JavaScriptは `88.0` を `88` として保持する）。
* 型情報を別配列（`types` 等）で返すことはしない。値自体が自己記述的であるため不要であり、UNIONなどで列内の型が混在しても表現が破綻しない。

この表現は §3 の `.mode json` と共通の規則とする（両者で異なる表現を持たない）。

**既知の制約:** JSONの数値として正確に表現できる整数は 2^53 - 1 までであり、SQLiteのINTEGER（64bit）の全範囲を表現できない。2^53 を超える整数は、JavaScriptのように言語自体に64bit整数型を持たない処理系で精度が失われる（エラーは発生せず、値が静かにずれる）。分散IDやナノ秒精度のタイムスタンプを含む既存データベースを `.load` で取り込む場合は注意が必要。Go・Rust・Java・C# など64bit整数を扱える言語のドライバは、JSONの数値を倍精度浮動小数点へデコードせず、数値トークンを文字列として取得してから整数へパースすること（Goなら `json.Number`、Rustなら `serde_json` の arbitrary precision）。これによりサーバー側が数値で出力していても値は保たれる。

### 実装者への注意（本体・ドライバ双方の契約）

* **1行書いたら必ずフラッシュする。** 本体側は1レスポンスを書くごとに、クライアント側は1リクエストを送るごとにフラッシュしなければならない。パイプはバッファリングされるため、これを怠ると双方が相手の入力を待ち続けてデッドロックする。Goの `bufio.Writer` を使う場合はリクエストごとに `Flush()` を呼ぶこと。
* **stderr を塞がない。** クライアントが子プロセスの stderr をパイプに繋いだまま読み捨てないと、ログでバッファが埋まった時点で子プロセスがブロックする。読まないなら `/dev/null` へ向けること。
* **EOF は接続断を意味する。** 子プロセスが異常終了した場合、クライアントの行読み取りはEOFを返す。ドライバはこれを検出して終了コードを回収すること（回収しないとゾンビプロセスが残る）。
* **終了は stdin のクローズで行う。** `close` op または stdin のクローズで子プロセスは自ら終了する。ドライバの `close()` は「stdin を閉じる → 一定時間待つ → まだ生きていれば SIGTERM」という段階的な実装が望ましい。

### クライアントドライバ

各言語向けのクライアントドライバは、**本リポジトリには含めず、別プロジェクト `san-db-ox-clients` で提供する**。本リポジトリが定めるのは、本節のプロトコル仕様までである。

本体を「Goツールチェーンだけで完結する」状態に保つための切り分けであり、複数言語ぶんのランタイム導入は本体のビルド・テストに一切不要である。本体側に残す接続テストは、Goで書いたstdioクライアントのみとする。

> なお、本プロトコルはサブプロセスとパイプを扱える処理系であれば**専用ライブラリなしで直接扱える**。ドライバは利便性のための薄いラッパーであって、利用の前提条件ではない。

## 8. 想定される使われ方

SanDBox はネットワーク待受を持たないが、**外部ツールでトランスポートを外付けし、ネットワーク越しに利用されることを想定している**。代表的なのは `socat` の `EXEC` アドレスと `--serve-stdio` を組み合わせる形で、これによりTCP/UNIXドメインソケットのサービスが**本体側の実装ゼロで**成立する。口を開ける判断と責任は完全に運用者側にあり、SanDBox 自身は `net` を import しない（§10）。

**この使われ方が設計・実装・テストに課す前提が2つある。**

**1. 接続ごとに別プロセス・別DBになる。** これは SanDBox の仕掛けではなく、`socat` の `fork` オプションの挙動である（`fork` を指定した socat は接続を受理するたびに自身を fork し、子側で `EXEC:` のコマンドを exec する。`inetd` 以来の古典的なパターンで、相手が何であっても同じ）。SanDBox はインメモリDBであり、かつ**プロセス＝セッション**（§7）であるため、プロセスが分かれればDBも分かれる。A の INSERT は B から見えず、A の `snapshot` の結果も B のメモリには反映されない。

`fork` を外しても解決しない——子プロセスは1つだけになりDBも1つになるが、その接続が切れると socat 自体が終了し、次の接続を待てなくなる。つまり**「1つのDBを立てっぱなしにして複数の接続を順番に捌く」構成は、トランスポートを外付けする方針では作れない。** これは避けられない限界であり、共有が必要な場合は子プロセスを1つだけ起動して保持する常駐アプリを利用者側が書くことになる（そのアプリがネットワークを提供する側になる）。

**2. 同一バイナリから複数プロセスが同時に起動される。** 上記の帰結として、同じ実行ファイルを複数のプロセスが同時に読み込む状況が日常的に発生する。フッターの読み出しが競合しないこと、`.snapshot` が同じパスへ同時実行されても壊れたファイルが観測されないこと（§11のアトミック書き込み）は、この前提のもとで担保する必要がある。**テストもこの状況を含めること**（`.claude/rules/testing.md`）。

なお、外部公開時には認証が一切存在しない点に注意が必要である。到達できる者は誰でもDDLを含む任意のSQLを実行できるため、`--read-only`（§2）との併用を前提とする。**具体的な接続方法・セキュリティ設定は本書の範囲外**であり、`san-db-ox-clients` のドキュメントで扱う。

### Docker

```dockerfile
FROM scratch
COPY san-db-ox /san-db-ox
ENTRYPOINT ["/san-db-ox", "--serve-stdio"]
```

単一バイナリであるため `FROM scratch` で動作する。ログを永続化したい場合は `2> /path/to/log` へのリダイレクトや、Docker/systemd の既存ログ基盤に委ねる（§0）。

## 9. 主なユースケース (Use Cases)

1. **CI/CD・E2Eテストの爆速化 (Instant Test DB)**
   * テーブル構築・シードデータ投入済みのバイナリを1個置くだけで、1秒未満でメモリ上へテスト環境が立ち上がり、後処理も不要。
   * `-c` / stdinによるバッチ実行（§5）と終了コードで、シェルスクリプトや Makefile からそのまま検証できる。
2. **「データ状態付き」でのバグ再現・チーム共有 (Executable Snapshots)**
   * 不具合が起きたデータ状態を `.snapshot bug_123` でバイナリ化して共有。受け取った側は実行するだけで全く同じDB環境を即座に再現。
   * 共有先が異なるOSを使っている場合は、そのOS向けの空バイナリを起動し、`.load` でデータをメモリへ取り込んだ上で `.overwrite` を実行することで、同じデータをそのOS向けの実行ファイルとして作り直せる（§4参照）。
3. **他プログラムへの結合 (Embeddable via stdio)**
   * 任意の言語から子プロセスとして起動し、JSON Lines で対話（§7）。ネットワーク設定・認証設定・常駐プロセスの管理が一切不要。
   * 各言語向けのクライアントドライバは別プロジェクトで提供する（§7）。
4. **閲覧用デモ環境の一時公開 (Read-only Demo)**
   * `socat` でトランスポートを外付けし（§8）、`--read-only` で書き込みを封じることで、バイナリ1つと1行のコマンドから閲覧用のデモ環境を立てられる。サンプルデータを埋め込んだバイナリを配って「これを実行して繋いでください」で済む。
   * **ただし接続ごとに独立したDBになる**（§8）。複数人が同じデータを書き換えながら共有する用途には使えない。認証も無いため、公開範囲は `bind=127.0.0.1` やSSHポートフォワードで絞ること。この2点は README でも必ず併記する。
5. **エッジ・CLIツールのポータブルな状態管理 (Portable Data Capsules)**
   * 外部DBに依存せず、実行ファイル単体で高速処理とファイル単位のスナップショット保存を実現。
6. **環境構築ゼロのSQL学習・ハンズオン (Zero-Setup SQL Sandbox)**
   * インストールや認証設定なしで、バイナリを叩くだけで即座にフル機能のSQL（View/Index/Trigger/Transaction）を学習・実験。
   * Windows / macOS / Linux 問わず、実行ファイルをダブルクリック（またはターミナルから起動）するだけでREPLが立ち上がるため、WSL2等の追加セットアップを必要とせず初学者でも即座に試せる。
7. **既存SQLite資産との橋渡し (SQLite Interop)**
   * `.snapshot --sqlite` でSQLiteファイルを吐き、GUIツールやpandas等の既存エコシステムへ渡す。`.load` で既存のSQLiteデータベースを取り込む（§6）。

## 10. ライブラリアーキテクチャ

SanDBox は、**インメモリSQLエンジンのライブラリ（`engine` パッケージ）**を核とし、スタンドアロン実行ファイルは、その `engine` を用いて構築された「1つのリファレンス実装」として位置づける。

### レイヤー構成

```
san-db-ox/
├── engine/              ← 【ライブラリ本体】インメモリSQLエンジン
│                            （modernc.org/sqlite ラッパー、Go関数呼び出しのAPI、
│                             永続化インターフェース、自身の実行ファイルを
│                             上書きする Overwrite を提供）
│
└── cmd/san-db-ox/       ← 【アプリ】engineを利用した単一バイナリRDBMSの実装
                             （REPL、バッチ実行、stdioプロトコル）
```

具体的なファイル構成（`engine.go`, `persist.go`, `main.go`, `repl.go`, `stdio.go` 等）は実装時に決める（詳細は `.claude/rules/directory-structure.md` 参照）。ここでは2つのディレクトリの役割分担のみを示す。

### 責務分担

| | `engine`（ライブラリ） | `cmd/san-db-ox`（アプリ） |
| :--- | :--- | :--- |
| SQL実行 | Go関数呼び出し（単発実行の `db.Query()`/`db.Exec()` 等、および独立したクライアント単位で `BEGIN`/`COMMIT` をまたぐ `db.Session(ctx)`）を提供 | `engine` のAPIを呼び出すだけ |
| ネットワークI/F | **持たない**（`net`・`net/http` への直接依存なし） | **持たない**（同上。外部公開はトランスポートの外付けにより運用側が行う。§8） |
| アクセス制御 | 制限なし | 制限なし（§2） |
| 永続化 | 汎用的な読み書き（任意のファイル、`io.Writer`/`io.Reader`）＋ 自身の実行ファイルへの上書き（`Overwrite`）＋ SQLiteファイルへの書き出し（`Export`） | `.snapshot` / `.overwrite` / `.load` から呼び出すだけ（§4, §6） |
| ログ出力 | **行わない**（エラーは戻り値で返す） | stderr へ出力する（§0） |
| 用途 | 他のGoアプリに組み込む内蔵DB層（sqliteファイルの代替） | CI/CDテスト、他言語からの結合、ポータブル配布 |

### 設計原則: ネットワークI/Fを持たないことによる安全性

`engine` パッケージは、Goの関数呼び出しでのみアクセスできる。ネットワーク越しの入出力機能を実装しないため、他のGoアプリへ組み込んだ場合、外部からの通信経路は**そのアプリ自身が明示的に作らない限り一切存在しない**。これは「弾くロジックを書いて防御する」のではなく、「弾く手段が構造的に存在しない」ことによる安全性であり、`net`・`net/http` をimportしないことはコードレベルで検証可能である。

**この原則は `cmd/san-db-ox` にも同様に適用される。** 製品全体としてネットワーク待受を持たない。CIで「`net/http` が推移的にも現れないこと」「`net` を直接importしていないこと」を検証する。

ただし推移的依存には `net` パッケージが含まれる（内部SQLエンジン `modernc.org/sqlite` が使う `modernc.org/libc` 経由）。これはSQLiteドライバ実装自体の都合であり、ネットワークI/Oを行うコードを持つことを意味しない。

### 主要API

```go
// 開く
func Open(path string) (*DB, error)     // SQLiteファイル
func OpenSelf() (*DB, error)            // 自身の実行ファイルに埋め込まれたデータ

// 永続化
func (db *DB) Snapshot(path string) error  // 別名の実行ファイルを生成
func (db *DB) Overwrite() error            // 自身の実行ファイルを上書き（プロセスは終了しない）
func (db *DB) Export(path string) error    // SQLiteファイルとして書き出し
func (db *DB) Load(path string) error      // 他ファイルからデータのみ取り込み（種別自動判別）

// 検査（ファイルを開かずにフッター情報・種別のみ取得）
func Inspect(path string) (*FileInfo, error)

// セッション
func (db *DB) Session(ctx context.Context) (*Session, error)
func (db *DB) Close() error
```

**公開しないもの:** ユーザー定義のスカラー関数を登録するAPI（`modernc.org/sqlite` が持つカスタム関数登録機構のラッパー）は公開しない。APIの表面積を最小に保つため。必要になった場合は、ホストアプリ側でドライバへ直接登録する。

**`Snapshot` と `Export` の使い分け:** CLIでは `.snapshot --sqlite` の一語に統合しているが、**Goライブラリでは2つのメソッドを維持する**（`Snapshot(path, sqlite bool)` のような真偽値引数は呼び出し側で読みにくいため。CLIのコマンド体系とライブラリのAPIが1対1である必要はない）。 `Snapshot` は「エンジンバイト＋データ＋フッター」からなる**実行ファイル**を生成する。ライブラリとして組み込まれている場合、ここでの「エンジンバイト」はホストアプリのバイナリ全体であり、生成されるのはホストアプリの複製である。データだけを別ファイルに残したい場合は `Export` を使う。この区別は `Open` で開いたか `OpenSelf` で開いたかに依存しない（`Snapshot` は常に実行ファイルを、`Export` は常にSQLiteファイルを生成する）。

#### `OpenSelf`

`os.Executable()` で自身のパスを取得した上で、末尾フッターからデータを読み込む。起動時に前回の `Overwrite` が残した `.san-db-ox.old` 退避ファイル（§11参照）のベストエフォート削除も合わせて行う。

#### `Overwrite`

呼び出し元プロセス自身の実行ファイルを、現在のDB状態を埋め込んだ内容で上書きする。書き込み方式は §11 参照。成功時、ファイルの中身は差し替わるが、**呼び出し元プロセス自体は終了しない**（終了させるかどうかは呼び出し元の判断に委ねる）。

`engine` は「自分のどこまでがエンジンでどこからがデータか」をホストアプリに意識させない。ホストアプリ全体がそのまま「エンジン部分」として扱われ、その後ろにデータとフッターが付与される。

**利用上の注意:**
* ホストアプリが `/usr/bin/` や `C:\Program Files\` のような書き込み権限が必要なディレクトリに設置されている場合、`Overwrite` は権限エラーで失敗する。
* ホストアプリ自身が別の自己更新の仕組み（Squirrel/Sparkle等）を持つ場合、実行ファイル差し替えのタイミングが競合しうる。
* このAPIはGoアプリへの組み込みを対象範囲とする。

#### `Session`

`db.Query()`/`db.Exec()` はコネクションプールから借りた接続を1文だけ使って返す単発実行であり、これを使って `BEGIN` しても、後続の `COMMIT` が同じ接続に届く保証はない。「1つの独立したクライアントが、同じ接続上で複数の文にまたがるトランザクションを張る」用途には `Session` を使う。

```go
func (db *DB) Session(ctx context.Context) (*Session, error)

func (s *Session) Exec(query string, args ...any) (sql.Result, error)
func (s *Session) Query(query string, args ...any) (*sql.Rows, error)
func (s *Session) QueryRow(query string, args ...any) *sql.Row
// 上記それぞれの *Context 版、および db.Exec 等自体の *Context 版もある。

// 同じ文を繰り返し実行する呼び出し元（.import による CSV一括投入等）向け
func (s *Session) Prepare(query string) (*sql.Stmt, error)
func (s *Session) PrepareContext(ctx context.Context, query string) (*sql.Stmt, error)

func (s *Session) Close() error  // idempotent
```

### ライブラリとしての利用例

```go
import "github.com/amisonnet8/san-db-ox/engine"

// SQLiteファイルを開く（通常のsqliteファイルの代替として利用）
db, err := engine.Open("myapp.db")

// 通常のSQL操作
db.Exec("CREATE TABLE IF NOT EXISTS users (id INTEGER PRIMARY KEY, name TEXT)")
db.Query("SELECT * FROM users")

// データをSQLiteファイルとして書き出す
db.Export("myapp_backup.db")

// ホストアプリ自身の複製を、現在のデータ付きの実行ファイルとして生成する
db.Snapshot("myapp_with_data")

// ホストアプリ自身の実行ファイルを上書きする
db.Overwrite()

db.Close()
```

## 11. アーキテクチャ・技術選定

| 項目 | 内容 | 備考 |
| :--- | :--- | :--- |
| **開発言語** | **Go (Golang)** | 静的バイナリ生成、クロスコンパイル、マルチプラットフォーム対応。**CGOは使わない** |
| **ターゲットOS** | **クロスプラットフォーム対応（Linux / macOS / Windows）** | 全モードが全OS共通で動作。コンテナ運用（`FROM scratch` 等の軽量イメージ）はLinuxを優先する。配布物は各OS/アーキテクチャ向けの空（データなし）バイナリをあらかじめビルドして提供する |
| **内部DBエンジン** | `modernc.org/sqlite`（Pure-Go SQLite トランスパイル版） | CGO不要でクロスコンパイル容易、`database/sql` 標準インターフェース準拠。View, Index, Trigger, Transaction を含む完全な SQL 互換性を実績豊富な実装で低コストに担保 |
| **外部連携** | stdio（JSON Lines） + SQLiteファイル | §6, §7参照。ネットワークプロトコルは実装しない |

### バイナリ埋め込み方式（固定長フッター）

実行ファイル末尾へのデータ埋め込みは、**固定長フッター（トレーラー）方式**を採用する。

```
[Goバイナリ本体（エンジン部分）] [データブロブ（DB状態）] [フッター（固定32バイト）]
```

| フィールド | サイズ | 内容 |
| :--- | :--- | :--- |
| Magic | 8 bytes | 識別子 `"SANDBOX1"` |
| Version | 4 bytes | フォーマットバージョン（**big-endian**符号なし整数）。初版は `1` |
| DataOffset | 8 bytes | データブロブの開始オフセット（先頭からの絶対位置、**big-endian**） |
| DataLength | 8 bytes | データブロブの長さ（**big-endian**） |
| Reserved | 4 bytes | 将来拡張用 |

フッター中のすべての整数フィールドは **big-endian** でエンコードする。

* **読み込み:** `os.Executable()` で自身のパスを取得し、ファイル末尾から32バイトを `Seek` で読むだけでフッターを特定できる。ELF/Mach-Oのセクションヘッダ解析は不要。
* **書き込み（`.snapshot` 実行時、別名保存）:** 起動時に自身のエンジン部分のオフセット（0〜DataOffset、または末尾フッターが無い場合はファイル全体サイズ）のみをメモリ上に保持しておき、実際のエンジンバイト列は保存直前に読み直す（`modernc.org/sqlite` 込みのバイナリは10〜15MB級になるため、バイト列自体を常駐させない）。保存時は「エンジンバイト＋新データ＋新フッター」から新しいスナップショットを生成する。差分計算や再リンクは不要。書き込みは同じディレクトリに作った一時ファイルへ書いてから `rename` するアトミックな方式を採り、読み手が書きかけの不完全なファイルを観測することはない。また、データブロブの取得（後述の `Serialize`）は他セッションが書き込みトランザクションを実行中でないことを保証してから行うため、並行して書き込みが起きていても常に一貫したスナップショットになる。
* **書き込み（`.overwrite` 実行時、自己上書き）:** 同名（自分自身）への直接上書きは、実行中のファイルへの書き込みロックによりOSレベルで拒否される（Linuxの `ETXTBSY`、Windowsの `ERROR_SHARING_VIOLATION`）。これを回避するため、以下の手順を採る（Linux/Windows双方でPoC検証済み）。
  1. 実行中の自分自身を `<path>` → `<path>.san-db-ox.old` に `rename` で退避する（実行中ファイルの名前変更自体はLinux/Windows双方で許可される）
  2. 空いた元のパスへ新しい中身（エンジンバイト＋新データ＋新フッター）を新規書き込みする
  3. 退避ファイルの削除を試みる（Linuxはその場で成功。Windowsは実行中のためロックされ失敗するのが正常であり、次回起動時にベストエフォートで削除する）

  手順2の書き込みに失敗した場合は、手順1で退避したファイルを元のパスへベストエフォートで戻す。また、実行中のプロセスが `go run` によって生成された一時バイナリである場合（プロセス終了と同時にOSがファイル自体を削除するため、上書きしても無意味になる）、`.overwrite` は明示的なエラーで拒否する。
* **データなしの初回配布バイナリ:** 末尾にマジックバイトが見つからない場合は「エンジンのみ・データ空」として起動する。`go build` した素のバイナリがそのまま実行可能であり、`.snapshot` または `.overwrite` を実行して初めてデータ付きバイナリになる。
* この方式は自己解凍インストーラやJARファイル（ZIP中央ディレクトリの末尾探索）などで実績のある手法であり、OSローダーの実行にも影響を与えない。

### データブロブのシリアライズ方式（確定）

「データブロブ」＝インメモリSQLite DBの状態をバイト列化する方法として、**SQLite標準の `Serialize`/`Deserialize` API（`sqlite3_serialize()` / `sqlite3_deserialize()`）を使う方式を採用する**（実測検証済み、フォールバック不要と判断）。自前のシリアライズ形式は編み出さない。§6 の通り、この出力はSQLiteファイルの中身そのものである。

* **実際のAPI:** `modernc.org/sqlite`（v1.58.0で確認）が提供するのは `func (c *conn) Serialize() ([]byte, error)` と `func (c *conn) Deserialize(buf []byte) error` であり、**スキーマ名を渡す引数は無い**（常にmainスキーマが対象）。`conn` 型自体はunexportedだがメソッドはexportedなので、`database/sql` の `*sql.Conn` から `conn.Raw(func(driverConn any) error { ... })` を呼び、`driverConn` をローカルで定義したinterface（`interface{ Serialize() ([]byte, error) }` 等）に型アサーションすることで到達できる。
* **書き込み時（`.snapshot` / `.overwrite`）:** 上記の方法で取得した `Serialize()` の戻り値を、そのままフッター方式の「データブロブ」として書き込む。
* **起動時:** バイナリ末尾から読み込んだデータブロブを、同様の方法で取得した `Deserialize(data)` にそのまま渡すことで、SQLiteが内部的にインメモリDBとして再展開する。`modernc.org/sqlite` は内部で `SQLITE_DESERIALIZE_RESIZEABLE|SQLITE_DESERIALIZE_FREEONCLOSE` を指定して `sqlite3_deserialize()` を呼んでいるため、**復元後のDBは通常のDBと同様に拡張可能**（大量INSERTが可能。復元専用の固定サイズDBにはならないことを実測確認済み）。
* **接続共有モデル（`memdb` VFS）:** DSNは `file:/<n>?vfs=memdb&_busy_timeout=<N>`（`modernc.org/sqlite` が実装する `memdb` VFS）を採用する。名前が `/` で始まるDSNは、同一プロセス内であれば複数のコネクションが同じインメモリストアを共有する。`memdb` のロックはファイルベースDBと同種のSHARED/RESERVED/EXCLUSIVE機構で実装されているため、コネクション間のロック衝突時は `busy_timeout`（SQLite標準のbusy-handler機構）が正しく機能し、有界に待ってから諦める。当初検討していた `file:<n>?mode=memory&cache=shared`（shared-cache）は、ロック衝突時に `SQLITE_LOCKED_SHAREDCACHE` という別系統のエラーとなり、`busy_timeout` が効かないうえ、待機自体もアプリケーション側から `context` でキャンセルできず無期限にハングしうることが実測で判明したため不採用とした。他の全接続が閉じてもストアが解放されないよう、`Close()` まで保持し続ける「keeper接続」を1つ持つ（keeperはストアを生かすためだけに存在し、SQL文の実行そのものには使わない）。
* **`Deserialize` と複数コネクションの関係:** `Deserialize` はスキーマを匿名（無名）の `memdb` ストアとして内部的に開き直す実装になっており、呼び出したコネクション自身にしか結果が反映されない——同一DSNで後から開いた別コネクションからも見えない。そのため `Open`/`OpenSelf`/`Load` は、まず使い捨てのコネクションへ `Deserialize` した上で、SQLite標準のオンラインBackup API（`sqlite3_backup_*` 系。`modernc.org/sqlite` では `NewBackup`/`NewRestore` として公開）でその内容を「生きている」DB（keeper接続が保持するストア）へコピーする、という2段階の手順を踏む。Backup APIによるコピーはSQLite本来のB-tree/pager経由の複製であり、コピー先の全コネクション（Backup実行前から開いていたものも含む）から結果が見える。`Load` がこの仕組みで「生きている」DBへその場で上書きする形を取ることにより、`.load` 実行前から開いていた他のセッションも接続を失わずに新しいデータを参照できる。
* **`Export` の実装:** 同じBackup APIを、コピー先としてファイルDBへ向けて呼ぶ（§6）。SQLiteファイルの `Load` はその逆方向（ファイルDB → 生きているインメモリDB）となる。
* **既知の制約:** SQLite本体の `Serialize`/`Deserialize` 自体は非連続なバイト列を扱えず、理論上はデータベースサイズが2GB未満に制限される。ただし採用した `memdb` VFS にはそれとは別に `SQLITE_MEMDB_DEFAULT_MAXSIZE`（1GiB）というデフォルト上限があり、実測では約960MiB付近で `SQLITE_FULL` となることを確認済み——**実効的な上限は約1GiB**である。主要ユースケース（CI/CDテストDB、他プログラムからの結合、学習用サンドボックス等）では通常問題にならない想定だが、大容量データを扱う用途では制約となりうる。

## 12. 起動オプション

起動時のコマンドライン引数は、短縮フラグ（1文字）と長いフラグの両方を用意する。短縮フラグは大文字小文字の混在による覚えにくさを避けるため、**全て小文字**で統一する。この方針上、割り当てられる小文字が無い、あるいは短縮する必然性が薄いフラグには**短縮形を設けない**。

| 短縮 | 長い形式 | 型 | デフォルト | 役割 |
| :--- | :--- | :--- | :--- | :--- |
| `-c` | `--command` | string（複数可） | （未指定） | 指定されたSQL/ドットコマンドを実行して終了する（§5）。複数回指定可、指定順に実行 |
| `-m` | `--mode` | string | `list` | 出力形式。`list`/`column`/`csv`/`json`/`line`（§3の `.mode` と同一） |
| `-o` | `--snapshot-as` | string | （未指定） | `.snapshot` 実行時に使うデフォルトファイル名 |
| `-q` | `--quiet` | bool | `false` | 起動時のバナー・ログ出力を抑制する |
| `-t` | `--timestamp` | bool | `false` | 保存時にファイル名へタイムスタンプを付与するか（下記参照） |
| `-i` | `--snapshot-interval` | duration | `0`（無効） | 指定間隔で自動的に別名スナップショット保存を行う（例: `5m`, `1h`）。REPLモード・stdioモードで有効、バッチ実行では無効 |
| ─ | `--serve-stdio` | bool | `false` | stdioプロトコルモードで起動する（§7） |
| `-r` | `--read-only` | bool | `false` | 書き込みを伴うSQL・保存操作・ファイル書き出しを拒否する（§2） |
| `-v` | `--version` | bool | - | バージョン表示 |
| `-h` | `--help` | bool | - | ヘルプ表示 |

**モードの排他関係:** `--serve-stdio` と `-c` は同時に指定できない（使用法エラー、終了コード2）。いずれも指定されず、標準入力が端末であれば REPL、端末でなければバッチ実行として扱う。

**その他の排他関係:** `--read-only` と `--snapshot-interval` は同時に指定できない（使用法エラー、終了コード2）。読み取り専用モードは保存操作をすべて拒否するため、定期保存の指定と両立しない（§2）。

### タイムスタンプ付与

`.snapshot` 実行時、ファイル名に日時タイムスタンプ（`_YYYYMMDDHHMMSS`）を付与するかどうかを `--timestamp`（`-t`）で切り替えられる。**boolフラグ**であり、値の選択肢は持たない。

* **`--timestamp` を指定した場合:** 以下のルールでファイル名を生成する（ファイル名省略時・明示指定時、CLI起動オプション・`.snapshot` コマンドのいずれでも共通のルール）。
  1. ベースとなるファイル名（拡張子を除く部分）から、既存の `_YYYYMMDDHHMMSS` パターンがあれば取り除く（二重付与を防ぐ）。
  2. 拡張子の直前に新しい `_YYYYMMDDHHMMSS` を挿入する。
  3. 拡張子が省略されている場合、実行ファイル出力（既定）ならWindows環境で `.exe` を、SQLiteファイル出力（`--sqlite`）なら全OSで `.sqlite` を付与する。

  | ベースとなるファイル名 | 生成結果 |
  | :--- | :--- |
  | `san-db-ox`（ファイル名省略、実行中バイナリ名がベース） | `san-db-ox_YYYYMMDDHHMMSS` |
  | `mydb_20260101120000`（既存タイムスタンプあり） | `mydb_YYYYMMDDHHMMSS`（古いものは除去し差し替え） |
  | `mydb.exe` | `mydb_YYYYMMDDHHMMSS.exe` |
  | `mydb`（`-o mydb` で明示指定、Windows環境） | `mydb_YYYYMMDDHHMMSS.exe` |
  | `mydb`（`--sqlite` 指定時） | `mydb_YYYYMMDDHHMMSS.sqlite` |

  **ベース名にハイフンが含まれていてもよい**（区切り文字は `_` 固定のため、`san-db-ox` はそのまま扱える）。

* **`--timestamp` を指定しない場合（デフォルト）:** タイムスタンプは付与せず、指定されたファイル名（拡張子が省略されていれば上記の規則で補完したファイル名）をそのまま使う。同名ファイルへの上書きが起きうる。

このオプションは起動時のデフォルト値として機能するが、`.snapshot` コマンド実行時にも同様のオプションでその場で上書き指定できる。

```
.snapshot bug_123 --timestamp
.snapshot bug_123 --sqlite --timestamp
```

`.overwrite` にはファイル名指定の概念がないため（自分自身のパスに固定）、`--timestamp` オプションは適用されない。

### 定期スナップショット（`--snapshot-interval`）

`--snapshot-interval`（`-i`）を指定すると、その間隔で自動的に別名スナップショット保存を繰り返す。

* **用途:** 「長時間の対話セッション中に保存し忘れてクラッシュし、全データを失う」事故を防ぐ保険機能。§1 の「保存は明示操作のみ」という原則に対する、**オプトインの例外機能**という位置づけ。
* **保存方式:** 別名保存（`.snapshot` 相当）のみに対応する。自己上書き（`.overwrite` 相当）の定期実行は、実行中ファイルへの頻繁な書き換えによるリスクが高いためサポートしない。出力形式は実行ファイル（既定）とし、SQLiteファイルでの定期保存は行わない。
* **`--read-only` との同時指定は使用法エラー**（終了コード2）。
* **ファイル名:** `--snapshot-as` / `--timestamp` の設定に従う。`--timestamp` を指定した場合はタイムスタンプ付きファイルが間隔ごとに生成され続けるため、ファイルの肥大化・整理は §4 と同様に運用側に委ねる。固定ファイル名で上書きし続けたい場合は `--timestamp` を指定しない（デフォルト）。

## 13. ライフサイクル・動作フロー

```text
[1. 起動]
   └─> ./san-db-ox を実行
   └─> バイナリ末尾からデータを読み込み、メモリ（RAM）へ展開
   └─> 前回の .san-db-ox.old 退避ファイルがあればベストエフォート削除
   └─> モード判定
        ├─> --serve-stdio         : stdioプロトコルモードへ（§7）
        ├─> -c 指定あり            : バッチ実行モードへ（§5）
        ├─> stdin が端末でない     : バッチ実行モード（stdinをスクリプトとして読む）
        └─> それ以外               : 起動バナーを表示し、REPLを開始

[2. 運用・クエリ実行]
   └─> 全モードで DDL / DML / TCL のすべてを実行可能（アクセス制御なし、§2）

[3. 保存（別名）]
   └─> .snapshot コマンド（または stdio の snapshot op）を実行
   └─> メモリ上の最新状態 ＋ エンジン本体をパッキング
   └─> 新しい別名実行ファイル（例: san-db-ox_20260831_150000）を生成して出力

[3'. 保存（自己上書き）]
   └─> .overwrite コマンドを実行（明示操作のみ）
   └─> 自分自身を <path>.san-db-ox.old へ退避 → 空いた元のパスへ新しい中身を書き込み（§11）
   └─> 成功したらそのままプロセスを終了（この操作のみ、保存と終了が同時に起きる）

[3''. SQLiteファイルへの書き出し]
   └─> .snapshot --sqlite <FILE> を実行 → SQLiteファイルを生成（§6）

[4. 停止（REPLモード）]
   └─> 通常の終了手段: .exit / .quit コマンド、または標準入力のEOF（Ctrl+D）
   └─> Ctrl+C（SIGINT）は対話端末では終了ではなく中断コマンドとして扱う（sqlite3のシェル準拠）:
        ├─> クエリ実行中に押すと、そのクエリだけを中断してプロンプトへ戻る（プロセスは終了しない）
        ├─> アイドル時（クエリ非実行中）に1回押すと、入力中の複数行分の未確定なSQLを破棄して
        │    プロンプトを出し直すだけで、プロセスは終了しない
        ├─> アイドル時に間に新しい入力行を挟まず連続で2回押すと、そこでプロセスを終了する
        │    （終了コード1。新しい入力行を1行でも読むと連続回数はリセットされる）
        └─> 標準入力が対話端末でない場合はこのハンドラを一切登録せず、SIGINTは通常の
             プロセス終了として扱われる
   └─> SIGTERMを受信した場合はプロセスを終了する（自動保存は行わない）

[4'. 停止（バッチ実行 / stdioモード）]
   └─> バッチ: 全ての文の実行完了、またはエラーによる中断で終了（終了コードは §5）
   └─> stdio: stdin の EOF、または close op で終了
   └─> SIGINT ハンドラは登録しない（通常のプロセス終了）
   └─> いずれも自動保存は行わない

[5. 共通]
   └─> どの終了経路でも、メモリ上のデータは保存されず消える（揮発性が前提）
```

### 起動時バナー

REPLモードでのみ、起動時にバナーを表示する。表示内容はバージョン、埋め込みデータの有無・スナップショット名。`.status` のような専用コマンドは設けず、起動時にこのバナーで一度提示することに一本化する。`-q`/`--quiet` 指定時はバナー全体を抑制する。バッチ実行・stdioモードでは表示しない。

**データあり:**
```
SanDBox v0.1.0
Loaded snapshot: mydb_20260901120000
Enter ".help" for usage hints.
```

**データなし:**
```
SanDBox v0.1.0
No embedded data. Starting with an empty in-memory database.
Enter ".help" for usage hints.
```

**読み取り専用モード（`--read-only`）:** 上記に加えて読み取り専用である旨の1行を表示し、`.help` の内容も拒否される操作を除いたものに差し替える（§2）。
```
SanDBox v0.1.0 (read-only)
Loaded snapshot: mydb_20260901120000
Enter ".help" for usage hints.
```
